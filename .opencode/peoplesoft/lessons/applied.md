  `"PeoplecodeMetadata_*": false` 與 `"PeoplecodeMeetadata_*": false`

  deny」檢查項；test-scenarios 加 F4。
- 套用：本 commit；後續正式整合（預定歸 ps-metadata-flow）待管理者
  提供該 server 的確切註冊名與完整工具清單。

- 正式整合（2026-07-27）：工具＝`find_field_usage`（fieldName／pageName／
  componentName）與 `search_component_metadata`（keyword）。開放給
  ps-ui-flow／ps-metadata-flow（定位優先步驟）與 ps-auditor（任務 C
  反查角度）；**定位線索不作 evidence**（契約仍僅 CHUNK／SQL 兩種），

  「不存在」證據，必回退 cookbook／ES 正規管道；auditor 任務 C 需
  兩角度交叉才可列疑似遺漏；F5 加對應檢查點。

  （aeApplid）→ 開放 ps-ae-flow（AE 結構定位優先）與 ps-metadata-flow

- 套用：本 commit；測試情境 G1／H1 對齊、G2 加「00-overview 零改動」

### L3 稽核只寫記分卡、跳過回灌——交付物完成後尾端步驟被丟（2026-07-27）
- 症狀：/ps-audit 產出 90-audit.md（PASS 8／FAIL 2／PARTIAL 2）後即
  結束，checklist 沒有任何 A<n> 補查行；且模型自創契約外狀態
  partial_pass。
- 根因：小模型寫完主要交付物即視為任務完成，排在其後的步驟（回灌、

- 落點：機械化順序——回灌**先於**記分卡（非 PASS ≥ 1 而 checklist

  （網住自創狀態）；命令加結束前 read checklist.md 自檢；模板加
  順序約束註記；H1 改致命檢查點＋狀態詞彙檢查。
- 套用：本 commit（ps-deep-research／ps-audit 命令／audit-template／
  test-scenarios H1）。
- 後續確認（2026-07-27）：舊版 90-audit 的「已回灌」節其實列好了
  5 個 A 項——模型**在報告裡聲稱已回灌，實際檔案一行未寫**
  （填表代替做事：模板有該節，就把它當一般章節填完）。遷移時已把
  這 5 項搬進 checklist.md。新順序（checklist 先寫、報告節只准抄錄
  實際行）＋結束前 read 自檢即針對此機制。

### L8 task 委派 JSON 截斷——整份檔案被貼進委派 prompt（2026-07-27）
- 症狀：invalid[tool=task, json parsing failed]，出現於寫完領域
  markdown 之後（打勾前快驗附近）。
- 根因：與 L2 同族（單次輸出過長被截斷）——模型剛寫完檔，順手把
  整份內容貼進給 auditor 的委派 prompt。auditor 本就有 read 權限
  （任務 A 第一步即「Read 目標檔」），委派只需要檔案路徑。
- 落點：機械化——委派瘦身規則（prompt 約 30 行上限；禁貼檔案／
  報告全文；驗檔委派只傳路徑）；task 失敗 → 縮短重委派、失敗 2 次
  標 ⚠ 跳過；SOP-9 補條目；新增 F6 測試情境（總數 37）。
- 套用：本 commit。
- 探針結果（2026-07-27）：輸出上限探針**能完整數到 3000**（輸出
  ≥ 約 8K tokens）——輸出 token 上限**不是**瓶頸。截斷／壞格更可能
  是「長結構化 JSON 的格式可靠度」問題（A3B 長輸出時跳脫／閉合
  出錯機率隨長度上升）。結論：瘦身與小檔規則維持不變（治發生面）；
  伺服器端唯一高價值槓桿＝ **tool-call 約束解碼**；不必追「加大
  輸出上限」。
- 追記（2026-07-30）：輸出偶見 `</think>` 等內部標記洩漏＝chat
  template／reasoning parser 未對齊（Qwen3 系混合思考模型），且
  是 JSON 壞格的可能來源之一。SOP-10 加對齊檢查與「關閉 thinking」
  評估項（工具密集用途通常更穩更快）；lint 加髒標記污染檢查。

### L12 一檔一行工單讓「紙上打勾」有機可乘——id 修復改走 lint 清單手術式（2026-07-30）
- 症狀：A29~A39 兩批跑完＋輪次 6 稽核，lint 縮寫 id 僅 14→13

  檔內逐筆的 id 修復被靜默跳過；「逐字取回傳」規則存在但**缺交付
  驗證**（沒有人核對修了哪幾筆）。
- 落點：(1) **修復必附收據**：舊→新 id 對照表，無收據不得打勾；
  (2) **lint 清單驅動**：把 lint 輸出的 檔×id 清單直接貼進指令
  逐筆處理（原子化、可核對、模型不需自己找目標）；(3) 修復波
  前後各 commit 內部 git（快照）；(4) 受損檔走 SOP-4 部分還原；
  (5) 輪次 6 報告視為不可信，lint 歸零後以新 session /ps-audit
  重測（輪次 7）作畢業依據。
- 套用：本 commit（agent 硬規則／SOP-2）。
- 結果驗證（2026-07-30）：手術式一次修復 **13/13 全數成功**。
  成功要因＝拿掉模型的「自主發現」段、粒度降到原子、收據交付、
  lint 前後驗收。**通用原則入庫：確定性工具負責「找目標」與
  「驗結果」，模型只負責中間非它不可的工具操作**——任何
  「叫模型修東西」的場景都適用此形。
- 輪次 7 里程碑（2026-07-30）：首份全合規＋健康文件的全量體檢——
  證據 PASS 83%（91/110，趨勢 69→78→73→83）、UNVERIFIABLE 僅 3、
  縮寫 id 類 FAIL＝0。殘餘 FAIL 16（新組成待原因分類）與
  DISPUTED 28/68（41%，回到稽核員噪音帶）進入人工抽驗畢業程序：
  真問題定向收尾、噪音行政結案（打勾＋⚠人工判定誤報）並以本輪
  數字為該領域基準地板。
- 措辭更正（2026-07-30，管理者指正）：縮寫 id＝0 是**存量清零**
  （手術修復的成果），**不是類別根除**——寫入端防線（模板範例＋
  禁縮寫規則）尚未經歷大量新寫入的實戰。驗證計畫：斷鏈補課的新
  entity 檔（首戰）與新領域首輪 research（第二戰）寫完各跑 lint，
  新檔持續乾淨才可宣告根除。原則：**修好存量 ≠ 堵住流量，
  兩者要分開驗證**。

### L13 輪次 7 FAIL 16 的三家族——lint 盲區、稽核過嚴、手術缺驗貨（2026-07-30）
- 症狀分類：(A) 截斷 id 仍現身稽核＝**lint 盲區**（只掃「ChunkId」
  前綴寫法，表格等其他位置的 8 碼漏抓，手術只修了看得見的）；
  (B) case mismatch／wrong_line／count_mismatch＝**稽核過嚴＋時效**
  （程式碼大小寫不敏感；quote 命中行號漂移；線上 DB 筆數本來會變）；
  (C) data flow 表無 chunk id、修復 id 內容不符 claim＝**真缺陷**
  （證據義務未履行；手術重取抓錯 chunk 仍硬填——缺「回傳必含原
  quote」的驗貨步驟）。
- 落點：機械化——(1) lint 廣域截斷偵測（任何位置的獨立 8 碼 hex
  含字母者）；(2) auditor 比對正規化（大小寫不分、空白摺疊）＋
  PASS(LINE_DRIFT)＋FAIL(STALE_DATA)（時效與造假分流）；
  (3) 修復前驗貨：重取 ChunkText 必含原 quote 才准寫入，抓錯禁止
  硬填；(4) STALE_DATA 修法＝更新數字。
- 待決：ES 查無那批取決於「索引近期是否重建」（是→SOP-11 正常
  死亡重取；否→id 本身有誤）。
- 套用：本 commit。
- 抽查解謎（2026-07-30）：「ES 查無」實為**假死**——程式碼存在，
  是 Component 事件（PreBuild／PostBuild）。死因＝定位鍵用錯：
  Component 層級 PeopleCode **沒有 Record.Field**，正確路徑＝
  Component 名搜檔 → get_file_structure → 按 Event 挑單元；拿事件名
  當全庫關鍵字＝滿庫都是、等於沒搜。落點：peoplecode-flow 加

  確定性障礙**——fresh session 通常一次就過；與 auto-compact、
  長 run 劣化同屬「session 壽命」病族，但發作點在單一生成內。
- 對應（已存在，本課記錄對應關係）：auto-loop 的逾時熔絲鏈＝
  人工「中斷→新 session 重跑」的自動版——session 逾時→taskkill
  整樹→唯讀一致性檢查→下一圈 fresh session 重跑同相位→連續
  2 次逾時才熔斷給人工。checklist 打勾只在完成後發生＝中斷零
  進度損失（檔案是狀態、session 是耗材）。
- 落點：SOP-9 加症狀處置（互動模式：見鬼打牆直接中斷重跑，不用等；
  自動模式：信任熔絲；timeout 可依領域常態調短加快反應）。
- 代價入帳：自動模式一次鬼打牆＝白燒一個 timeout slot（30~45 分）
  ——overnight batch 可接受；不做「重複輸出偵測」的提前熔斷
  （啟發式誤殺風險 > 省下的時間，L21 過敏教訓同理）。
- 套用：本 commit（SOP-9）。

- 原則：**跨腳本的輸出格式是 API**——改標題／改輸出前先 grep
  「誰在解析它」；以及**整合點要有端到端檢查**，單元全綠證明不了
  管線通。
- 套用：本 commit（auto-loop）。
- 追記（2026-08，雙 BOM 第二種面貌）：同一個搬運雙 BOM，症狀依**檔案
  結構**而異——檔首是註解（lint）→ 執行期「'#' 不是 cmdlet」；
  檔首註解後接 `param()`（auto-loop）→ **解析期 InvalidLeftHandSide**
  （多出的 FEFF 讓第 1 行變成一個「指令」，`param()` 不再是檔案第一個
  語句 → 被當函式呼叫解析 → 裡面的預設值賦值全非法，錯誤指向
  param 區塊各行）。兩者根因相同、修法相同（ps-fs-doctor -FixBom）。

  會偽裝成完全不同的錯誤**——診斷要看根因不看訊息措辭。

### L46 記事本之謎——PowerShell 挑 .ps1 shim，cmd.exe 用檔案關聯把它「開啟」（2026-08）
- 症狀：loop 開跑後**每圈跳出記事本**、關掉才繼續；管理者觀察
  「看起來沒找 opencode，直接就走完流程」。
- 根因（在外環不在模型）：npm 同時裝 `opencode`／`opencode.cmd`／
  `opencode.ps1`，而 **PowerShell 的 `Get-Command` 優先回 .ps1**
  （它把 .ps1 當一等公民）。auto-loop 把該路徑交給 `cmd.exe` 執行——
  **Windows 對 .ps1 的預設「開啟」動作是記事本**（防止雙擊誤執行的
  安全設計）→ 記事本開啟並**阻塞**；關掉後 cmd 回 **exit 0** →
  外環判定「session 正常結束」→ 整圈空轉、模型從未被呼叫。
  腳本註解早寫著「npm shim 是 .cmd，經 cmd.exe 呼叫最穩」，
  **解析卻沒挑 .cmd**——註解寫對、程式沒做。
- 落點：機械化——`Select-OpencodeShim`：`Get-Command -All` 後
  **按 .cmd → .exe → .bat 優先序挑**；一個都沒有就 exit 2 並明說
  「cmd.exe 會用檔案關聯開啟它（記事本）而不是執行它」；
  Preflight 印出解析結果與候選數。
- 附帶硬化（同 L1 覆寫表原則）：內建 agent 覆寫檔（general／explore／
  scout）只封了 4 個 MCP，**bash 沒列＝預設開**——委派漏到內建時
  仍可執行 shell。已補 `bash/write/edit/webfetch: false`
  （本案非此因，但同族側門要一起封）。
- 原則：**exit 0 只代表「那個東西結束了」，不代表「那個東西是你以為的
  東西」**——外環驗收要驗「做了什麼」，連「呼叫到誰」都要先驗對。
- 套用：本 commit（auto-loop／三個內建覆寫檔）。

### L48 監測門檻要照實測基線設——過敏警告訓練人忽略警告（2026-08）
- 症狀：新加的「輸出沉默偵測」門檻設 10 分鐘，第一圈就報警
  「輸出已靜止 11 分（疑卡在工具呼叫）」——但**同一天的實測基線**是
  健康的 audit session 沉默約 30 分、總計 35 分正常完成。
- 根因：門檻憑直覺設（「10 分鐘沒動應該有問題吧」），沒有用**手上
  已有的實測數據**校準。委派期間 subagent 的輸出不流到父行程 stderr，
  「安靜」是這個工作型態的常態而非異常。
- 危害：過敏警告比沒有警告更糟——每次都叫會訓練使用者忽略它，
  真正的停滯訊號被淹沒（狼來了）。
- 落點：門檻 10 → **20 分**，且措辭改中性（「委派期間長時間無輸出屬
  常態，實測健康可達 30 分；接近逾時上限仍無輸出才需查通道」）。
- 原則：**任何門檻（逾時、沉默、重試次數）都要用實測基線設，不用
  直覺設**；同一原則已用於 timeout 校準（實測 ×1.5），警告門檻同理。
  沒有基線數據時，先跑一輪收集，別急著設。
- 套用：本 commit（auto-loop）。

### L49 判定所依賴的值自己讀不到——外環的裁判瞎了，卻照樣宣判（2026-08）
- 症狀（第一次完整 auto-loop 實跑）：console 顯示
  `SESSION(audit) 結束 exit= 耗時 34 分`——**exit 後面是空的**；
  跑完最後停在「連續 2 次 session 錯誤」，但 out/err 檔看不出任何錯誤，
  兩圈其實都正常完成（未勾 4／已勾 6／稽核輪次 20）。
- 根因：`Start-Process -PassThru` 取得的行程物件，在**只用
  `WaitForExit(ms)` 等待**時 `.ExitCode` 常為 `$null`（PowerShell 已知
  行為：handle 未被快取住，行程結束後拿不回結束碼）。而
  `$null -eq 0` 是 **false** → `$sessionOk` 恆假 → **每個正常結束的
  session 都被記成錯誤**，第 2 圈就湊滿熔絲停機。
- 更嚴重的第二層：`SESSION_OK` 是三層畢業門的第一層——它恆假等於
  **這個框架永遠不可能畢業**，而且症狀只是「跑一跑就停」，不會有人
  往「畢業門壞了」的方向想。
- 併發的第三個 bug：err 尾巴用 `Get-Content` 讀但**沒給 `-Encoding
  UTF8`**，PS 5.1 預設 ANSI 解碼 → 中文全亂碼 → 唯一的診斷線索也讀不到。
  三個 bug 疊起來＝「停機了、原因欄空白、log 是亂碼」。
- 落點：機械化——**不相信 API 承諾，改要可觀測的事實**：
  1. cmd 命令尾巴接 ` & call echo %^ERRORLEVEL% > "<stamp>-<tag>.rc.txt"`
     （`%^ERRORLEVEL%` ＋ `call` ＝延後展開，取到的才是 opencode 的真碼），
     結束碼變成**磁碟上的檔案**，事後也能翻。
  2. 讀取優先序：rc 檔 → `Process.ExitCode` → **仍讀不到就視為 0 並大聲
     記一行警告**。方向刻意選「讀不到＝當正常」：反向已實證會把健康的
     run 誤停，而真正的失敗還有 err 檔／一致性檢查／轉移檢查三道網。
  3. 補 `$null = $p.Handle`（啟動後立刻快取 handle）＋結束後無參數
     `WaitForExit()` ＋ `Refresh()`；err 尾巴補 `-Encoding UTF8`。
- 原則：**任何「拿來下判定」的值，都要先確認自己讀得到**——外環的
  價值全在「確定性地判定有沒有做」，判定輸入是 `$null` 時，外環不會
  沉默失效，它會**照常宣判、而且判錯**。凡是判定輸入，一律
  (a) 落成可觀測的檔案，(b) 讀不到時走明確的預設值＋大聲記錄，
  絕不讓 `$null` 悄悄參與比較。
- 附帶：讀不到判定值時的預設方向，要選**「不會靜默終止整個流程」**的
  那一邊；讓熔絲寧可晚一圈才燒，也不要因為讀不到而誤燒。
- 套用：本 commit（auto-loop；19 項新驗證＋既有 73 項回歸全綠）。
