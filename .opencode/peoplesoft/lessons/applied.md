  `"PeoplecodeMetadata_*": false` 與 `"PeoplecodeMeetadata_*": false`

  deny」檢查項；test-scenarios 加 F4。
- 套用：本 commit；後續正式整合（預定歸 ps-metadata-flow）待管理者
  提供該 server 的確切註冊名與完整工具清單。

- 正式整合（2026-07-27）：工具＝`find_field_usage`（fieldName／pageName／
  componentName）與 `search_component_metadata`（keyword）。開放給
  ps-ui-flow／ps-metadata-flow（定位優先步驟）與 ps-auditor（任務 C
  反查角度）；**定位線索不作 evidence**（契約仍僅 CHUNK／SQL 兩種），

  「不存在」證據，必回退 cookbook／ES 正規管道；auditor 任務 C 需
  兩角度交叉才可列疑似遺漏；F5 加對應檢查點。

  （aeApplid）→ 開放 ps-ae-flow（AE 結構定位優先）與 ps-metadata-flow

- 套用：本 commit；測試情境 G1／H1 對齊、G2 加「00-overview 零改動」

### L3 稽核只寫記分卡、跳過回灌——交付物完成後尾端步驟被丟（2026-07-27）
- 症狀：/ps-audit 產出 90-audit.md（PASS 8／FAIL 2／PARTIAL 2）後即
  結束，checklist 沒有任何 A<n> 補查行；且模型自創契約外狀態
  partial_pass。
- 根因：小模型寫完主要交付物即視為任務完成，排在其後的步驟（回灌、

- 落點：機械化順序——回灌**先於**記分卡（非 PASS ≥ 1 而 checklist

  （網住自創狀態）；命令加結束前 read checklist.md 自檢；模板加
  順序約束註記；H1 改致命檢查點＋狀態詞彙檢查。
- 套用：本 commit（ps-deep-research／ps-audit 命令／audit-template／
  test-scenarios H1）。
- 後續確認（2026-07-27）：舊版 90-audit 的「已回灌」節其實列好了
  5 個 A 項——模型**在報告裡聲稱已回灌，實際檔案一行未寫**
  （填表代替做事：模板有該節，就把它當一般章節填完）。遷移時已把
  這 5 項搬進 checklist.md。新順序（checklist 先寫、報告節只准抄錄
  實際行）＋結束前 read 自檢即針對此機制。

### L8 task 委派 JSON 截斷——整份檔案被貼進委派 prompt（2026-07-27）
- 症狀：invalid[tool=task, json parsing failed]，出現於寫完領域
  markdown 之後（打勾前快驗附近）。
- 根因：與 L2 同族（單次輸出過長被截斷）——模型剛寫完檔，順手把
  整份內容貼進給 auditor 的委派 prompt。auditor 本就有 read 權限
  （任務 A 第一步即「Read 目標檔」），委派只需要檔案路徑。
- 落點：機械化——委派瘦身規則（prompt 約 30 行上限；禁貼檔案／
  報告全文；驗檔委派只傳路徑）；task 失敗 → 縮短重委派、失敗 2 次
  標 ⚠ 跳過；SOP-9 補條目；新增 F6 測試情境（總數 37）。
- 套用：本 commit。
- 探針結果（2026-07-27）：輸出上限探針**能完整數到 3000**（輸出
  ≥ 約 8K tokens）——輸出 token 上限**不是**瓶頸。截斷／壞格更可能
  是「長結構化 JSON 的格式可靠度」問題（A3B 長輸出時跳脫／閉合
  出錯機率隨長度上升）。結論：瘦身與小檔規則維持不變（治發生面）；
  伺服器端唯一高價值槓桿＝ **tool-call 約束解碼**；不必追「加大
  輸出上限」。
- 追記（2026-07-30）：輸出偶見 `</think>` 等內部標記洩漏＝chat
  template／reasoning parser 未對齊（Qwen3 系混合思考模型），且
  是 JSON 壞格的可能來源之一。SOP-10 加對齊檢查與「關閉 thinking」
  評估項（工具密集用途通常更穩更快）；lint 加髒標記污染檢查。

### L12 一檔一行工單讓「紙上打勾」有機可乘——id 修復改走 lint 清單手術式（2026-07-30）
- 症狀：A29~A39 兩批跑完＋輪次 6 稽核，lint 縮寫 id 僅 14→13

  檔內逐筆的 id 修復被靜默跳過；「逐字取回傳」規則存在但**缺交付
  驗證**（沒有人核對修了哪幾筆）。
- 落點：(1) **修復必附收據**：舊→新 id 對照表，無收據不得打勾；
  (2) **lint 清單驅動**：把 lint 輸出的 檔×id 清單直接貼進指令
  逐筆處理（原子化、可核對、模型不需自己找目標）；(3) 修復波
  前後各 commit 內部 git（快照）；(4) 受損檔走 SOP-4 部分還原；
  (5) 輪次 6 報告視為不可信，lint 歸零後以新 session /ps-audit
  重測（輪次 7）作畢業依據。
- 套用：本 commit（agent 硬規則／SOP-2）。
- 結果驗證（2026-07-30）：手術式一次修復 **13/13 全數成功**。
  成功要因＝拿掉模型的「自主發現」段、粒度降到原子、收據交付、
  lint 前後驗收。**通用原則入庫：確定性工具負責「找目標」與
  「驗結果」，模型只負責中間非它不可的工具操作**——任何
  「叫模型修東西」的場景都適用此形。
- 輪次 7 里程碑（2026-07-30）：首份全合規＋健康文件的全量體檢——
  證據 PASS 83%（91/110，趨勢 69→78→73→83）、UNVERIFIABLE 僅 3、
  縮寫 id 類 FAIL＝0。殘餘 FAIL 16（新組成待原因分類）與
  DISPUTED 28/68（41%，回到稽核員噪音帶）進入人工抽驗畢業程序：
  真問題定向收尾、噪音行政結案（打勾＋⚠人工判定誤報）並以本輪
  數字為該領域基準地板。
- 措辭更正（2026-07-30，管理者指正）：縮寫 id＝0 是**存量清零**
  （手術修復的成果），**不是類別根除**——寫入端防線（模板範例＋
  禁縮寫規則）尚未經歷大量新寫入的實戰。驗證計畫：斷鏈補課的新
  entity 檔（首戰）與新領域首輪 research（第二戰）寫完各跑 lint，
  新檔持續乾淨才可宣告根除。原則：**修好存量 ≠ 堵住流量，
  兩者要分開驗證**。

### L13 輪次 7 FAIL 16 的三家族——lint 盲區、稽核過嚴、手術缺驗貨（2026-07-30）
- 症狀分類：(A) 截斷 id 仍現身稽核＝**lint 盲區**（只掃「ChunkId」
  前綴寫法，表格等其他位置的 8 碼漏抓，手術只修了看得見的）；
  (B) case mismatch／wrong_line／count_mismatch＝**稽核過嚴＋時效**
  （程式碼大小寫不敏感；quote 命中行號漂移；線上 DB 筆數本來會變）；
  (C) data flow 表無 chunk id、修復 id 內容不符 claim＝**真缺陷**
  （證據義務未履行；手術重取抓錯 chunk 仍硬填——缺「回傳必含原
  quote」的驗貨步驟）。
- 落點：機械化——(1) lint 廣域截斷偵測（任何位置的獨立 8 碼 hex
  含字母者）；(2) auditor 比對正規化（大小寫不分、空白摺疊）＋
  PASS(LINE_DRIFT)＋FAIL(STALE_DATA)（時效與造假分流）；
  (3) 修復前驗貨：重取 ChunkText 必含原 quote 才准寫入，抓錯禁止
  硬填；(4) STALE_DATA 修法＝更新數字。
- 待決：ES 查無那批取決於「索引近期是否重建」（是→SOP-11 正常
  死亡重取；否→id 本身有誤）。
- 套用：本 commit。
- 抽查解謎（2026-07-30）：「ES 查無」實為**假死**——程式碼存在，
  是 Component 事件（PreBuild／PostBuild）。死因＝定位鍵用錯：
  Component 層級 PeopleCode **沒有 Record.Field**，正確路徑＝
  Component 名搜檔 → get_file_structure → 按 Event 挑單元；拿事件名
  當全庫關鍵字＝滿庫都是、等於沒搜。落點：peoplecode-flow 加

  確定性障礙**——fresh session 通常一次就過；與 auto-compact、
  長 run 劣化同屬「session 壽命」病族，但發作點在單一生成內。
- 對應（已存在，本課記錄對應關係）：auto-loop 的逾時熔絲鏈＝
  人工「中斷→新 session 重跑」的自動版——session 逾時→taskkill
  整樹→唯讀一致性檢查→下一圈 fresh session 重跑同相位→連續
  2 次逾時才熔斷給人工。checklist 打勾只在完成後發生＝中斷零
  進度損失（檔案是狀態、session 是耗材）。
- 落點：SOP-9 加症狀處置（互動模式：見鬼打牆直接中斷重跑，不用等；
  自動模式：信任熔絲；timeout 可依領域常態調短加快反應）。
- 代價入帳：自動模式一次鬼打牆＝白燒一個 timeout slot（30~45 分）
  ——overnight batch 可接受；不做「重複輸出偵測」的提前熔斷
  （啟發式誤殺風險 > 省下的時間，L21 過敏教訓同理）。
- 套用：本 commit（SOP-9）。

### L46 記事本之謎——PowerShell 挑 .ps1 shim，cmd.exe 用檔案關聯把它「開啟」（2026-08）
- 症狀：loop 開跑後**每圈跳出記事本**、關掉才繼續；管理者觀察
  「看起來沒找 opencode，直接就走完流程」。
- 根因（在外環不在模型）：npm 同時裝 `opencode`／`opencode.cmd`／
  `opencode.ps1`，而 **PowerShell 的 `Get-Command` 優先回 .ps1**
  （它把 .ps1 當一等公民）。auto-loop 把該路徑交給 `cmd.exe` 執行——
  **Windows 對 .ps1 的預設「開啟」動作是記事本**（防止雙擊誤執行的
  安全設計）→ 記事本開啟並**阻塞**；關掉後 cmd 回 **exit 0** →
  外環判定「session 正常結束」→ 整圈空轉、模型從未被呼叫。
  腳本註解早寫著「npm shim 是 .cmd，經 cmd.exe 呼叫最穩」，
  **解析卻沒挑 .cmd**——註解寫對、程式沒做。
- 落點：機械化——`Select-OpencodeShim`：`Get-Command -All` 後
  **按 .cmd → .exe → .bat 優先序挑**；一個都沒有就 exit 2 並明說
  「cmd.exe 會用檔案關聯開啟它（記事本）而不是執行它」；
  Preflight 印出解析結果與候選數。
- 附帶硬化（同 L1 覆寫表原則）：內建 agent 覆寫檔（general／explore／
  scout）只封了 4 個 MCP，**bash 沒列＝預設開**——委派漏到內建時
  仍可執行 shell。已補 `bash/write/edit/webfetch: false`

- 原則：**exit 0 只代表「那個東西結束了」，不代表「那個東西是你以為的

### L49 判定所依賴的值自己讀不到——外環的裁判瞎了，卻照樣宣判（2026-08）
- 症狀（第一次完整 auto-loop 實跑）：console 顯示
  `SESSION(audit) 結束 exit= 耗時 34 分`——**exit 後面是空的**；
  跑完最後停在「連續 2 次 session 錯誤」，但 out/err 檔看不出任何錯誤，
  兩圈其實都正常完成（未勾 4／已勾 6／稽核輪次 20）。
- 根因：`Start-Process -PassThru` 取得的行程物件，在**只用
  `WaitForExit(ms)` 等待**時 `.ExitCode` 常為 `$null`（PowerShell 已知
  行為：handle 未被快取住，行程結束後拿不回結束碼）。而
  `$null -eq 0` 是 **false** → `$sessionOk` 恆假 → **每個正常結束的
  session 都被記成錯誤**，第 2 圈就湊滿熔絲停機。
- 更嚴重的第二層：`SESSION_OK` 是三層畢業門的第一層——它恆假等於
  **這個框架永遠不可能畢業**，而且症狀只是「跑一跑就停」，不會有人
  往「畢業門壞了」的方向想。
- 併發的第三個 bug：err 尾巴用 `Get-Content` 讀但**沒給 `-Encoding
  UTF8`**，PS 5.1 預設 ANSI 解碼 → 中文全亂碼 → 唯一的診斷線索也讀不到。
  三個 bug 疊起來＝「停機了、原因欄空白、log 是亂碼」。
- 落點：機械化——**不相信 API 承諾，改要可觀測的事實**：
  1. cmd 命令尾巴接 ` & call echo %^ERRORLEVEL% > "<stamp>-<tag>.rc.txt"`
     （`%^ERRORLEVEL%` ＋ `call` ＝延後展開，取到的才是 opencode 的真碼），
     結束碼變成**磁碟上的檔案**，事後也能翻。
  2. 讀取優先序：rc 檔 → `Process.ExitCode` → **仍讀不到就視為 0 並大聲
     記一行警告**。方向刻意選「讀不到＝當正常」：反向已實證會把健康的
     run 誤停，而真正的失敗還有 err 檔／一致性檢查／轉移檢查三道網。
  3. 補 `$null = $p.Handle`（啟動後立刻快取 handle）＋結束後無參數
     `WaitForExit()` ＋ `Refresh()`；err 尾巴補 `-Encoding UTF8`。
- 原則：**任何「拿來下判定」的值，都要先確認自己讀得到**——外環的
  價值全在「確定性地判定有沒有做」，判定輸入是 `$null` 時，外環不會
  沉默失效，它會**照常宣判、而且判錯**。凡是判定輸入，一律
  (a) 落成可觀測的檔案，(b) 讀不到時走明確的預設值＋大聲記錄，
  絕不讓 `$null` 悄悄參與比較。
- 附帶：讀不到判定值時的預設方向，要選**「不會靜默終止整個流程」**的
  那一邊；讓熔絲寧可晚一圈才燒，也不要因為讀不到而誤燒。
- 套用：本 commit（auto-loop；19 項新驗證＋既有 73 項回歸全綠）。

  拿到完成時長後再照實測 ×1.5 收斂。設寬的成本是壞掉時多等一小時；設窄
  的成本是永遠量不到、而且每輪白燒。
- 順帶學到：稽核時長會**隨領域檔案數成長**（34 分 → >60 分），所以固定上限
  遲早都會錯——真正的解是「量得到 → 定期回頭校準」，不是猜一個大數字。
- 原則：**儀器要輸出結論，不是輸出原始資料**。凡是需要讀者跨檔比對才能得到
  的判讀，都要在事件發生的那一行就寫成人話——尤其當兩種可能的處置**完全
  相反**時（調上限 vs 查通道），沒有結論的資料只會讓人猜錯方向。
- 套用：本 commit（auto-loop；auto-all／SOP-14 的最壞時長公式同步更新）。

### L60 headless 的權限詢問不會被拒絕，它會永遠阻塞——而且 log 裡看不到（2026-08）
- 症狀（三輪、共約 4.5 小時才定位）：auto-loop 的 audit session 做完 13/15 個

  1. 先懷疑「稽核變慢」——用「56 分做完 13 檔」推出每檔 4.3 分、再推出

     輸出靜止 50 分」才發現 13 檔其實只花 11 分鐘，其餘 50 分是卡死。
     **把等待時間算進工作時間，就會憑空造出一個不存在的效能問題。**
  2. 接著懷疑通道死。但另開 console 測 MCP 正常——這其實不能證明什麼
     （新 session 開新連線，測不到卡住那個 session 手上那條）。
  3. 真正定位靠**互動式重跑同一個領域**：跳出 permission 提示、點 Allow
     後幾分鐘就跑完。SOP-2 升級梯的精神——自動化說不出為什麼，就降到人工看。

  （doom loop 之類會被自動擋下＝特性）」。**這句是錯的。** 查證後（opencode

  沒有 TTY 可以回答，"ask" 就是**永遠阻塞**。而權限提示是畫在 TTY 上的互動
  元件，stdout/stderr 重導到檔案後**在 log 裡一個字都看不到**。
- 第二個陷阱：TUI 上點「always allow」**只在該互動 session 內有效、不落檔**
  （官方文件明寫 "for the rest of the current OpenCode session"）。所以
  「我剛剛點過了」對 headless 完全沒用——每次開新 session 都會再撞一次。
  維護 session 一度建議去磁碟上找被改動的授權檔，那是**基於錯誤假設的
  無效指示**，白花使用者一次操作。
- 落點：檔頭註解全部改寫成查證過的事實；SOP-17 加第 0 條「必要前提」——
  在**本機全域** opencode.json（已註冊 MCP 的那份，含內部主機名、不進 repo）
  設 `"permission": { "doom_loop": "allow", "external_directory": "deny" }`。
  · **doom_loop 設 `deny`**（本課二次修正，實測定案）。初版寫 allow，理由是
    「稽核會對同一個 chunk id 重複取用＝正當行為，deny 會擋掉真驗證」——
    **那個理由建立在把 doom_loop 讀成『反覆呼叫』上，是錯的**：提示原文
    「continue after **repeated failures**?」管的是**反覆失敗**，重複成功的
    呼叫根本不會觸發它。錯誤的 allow 造成第二次事故：subagent 反覆讀一個
    不存在的 tool-output 檔，**靜止 30 分以上、零輸出、零提示**——

    deny＝快速失敗、看得見。**確定性失敗不該被重試**（L61 已立此原則），
    allow 等於在設定層打開無限重試，與該原則正面相反。
  · **【實測確認】觸發的是 `doom_loop`**：提示文字「continue after repeated
    failures?」、pattern 顯示 `invalid`。`invalid` ＝工具呼叫 JSON 被截斷
    （SOP-9 的老病），模型重試、再截斷，連續失敗即觸發 doom_loop 詢問。
    **因果鏈是：證據列變多 → 稽核回報 JSON 變長 → 截斷 invalid → 重試 →
    doom_loop → ask → headless 死鎖。** 這也解釋為什麼偏偏是那一個檔

    真正的緩解仍在 SOP-9。
  · 判斷過程的曲折要記下來：維護 session 先猜 doom_loop（對），被
    管理者的「subagent 會用暫存檔」觀察一講就改口 external_directory
    （**過度修正**），最後由管理者實際看到提示文字才定案。**兩次都是
    在沒有直接證據時用推理決定設定值**——正確做法是把兩個都設成不會
    死鎖的值，然後等實證。管理者那個觀察沒有白費：external_directory

- 原則零（管理者當場修正的那條）：**放寬權限前要先知道那個權限實際在

- 原則二：**看不見的阻塞比看得見的錯誤危險得多。** 這次的提示連 log 都

### L65 「看得見的失敗」勝過「看不見的重試」——無人環境的設定判準（2026-08）
- 事件鏈（同一個權限設定，兩次事故）：
  1. headless 稽核卡死 → 查出 `doom_loop` 預設 `ask`、無人可答（L60）。
  2. 維護 session 建議設 `allow`，理由是「稽核會重複取用同一個 chunk id＝
     正當行為，deny 會擋掉真驗證」。
  3. 改 allow 後**第二次卡死**：subagent 反覆讀一個不存在的 tool-output 檔，
     **靜止 30 分以上、零輸出、零提示**——比第一次更難查，因為連提示都沒了。
  4. 改 `deny` 後，同一份稽核**順利跑完**。
- 根因是**語意讀錯**：提示原文「continue after **repeated failures**?」管的是
  **反覆失敗的呼叫**，不是「反覆呼叫同一個東西」。重複成功的呼叫根本不會
  觸發它——建議 allow 的那個理由從一開始就不存在。而管理者早在第一次就
  把原文貼出來過，字面上寫著 failures。**證據在手上，讀錯了。**
- 三種設定的實際行為（實測）：
  · `ask`（預設）＝跳提示、headless 無人可答 → 卡死，**但看得見**
  · `allow`＝**無限重試失敗的呼叫** → 卡死，**完全看不見**
  · `deny`＝停止重試 → **快速失敗、看得見**
- 與 L61 的關係：L61 已立「確定性失敗不該被重試」（工具不存在、掛錯 server、
  檔案不存在——重試一萬次結果相同）。設 `allow` 等於**在設定層打開無限重試**，
  與框架自己的原則正面相反，而且是在模型層規則管不到的地方打開。
- 原則一：**無人環境的設定判準是「失敗看不看得見」，不是「會不會被擋」。**
  可見的失敗有人會查、有 log 可讀、熔絲抓得到；不可見的重試只表現為
  「靜止」，而靜止在任何儀表上都長得一樣。寧可多擋、不要靜默續試。
- 原則二（給維護者自己，本課第五次同型）：**使用者貼出的原文要逐字讀完再
  下判斷**。「repeated failures」四個字就在畫面上，我卻用自己腦中的
  「doom loop＝重複迴圈」去理解它，於是推出一個相反的設定值。
  同型前科：以為工具不存在（其實文件漏列）、以為回傳是索引副本（其實同源）、
  以為暫存在專案內（其實在專案外）、以為 audit 變慢（其實是卡死）。
  **共通點都是：手上有原始資料，卻用推理蓋過它。**
- 套用：本 commit（SOP-17 第 0 條、L60 落點修正）。

### L66 派工只指名一半、以及自己對自己並行——兩個舊教訓的漏網區（2026-08）
- 兩個獨立症狀，同一輪 loop 內先後出現：
  1. **稽核卡死**：err 顯示一次派出 6 個委派（A 項 3 批＋任務 C 3 批），

  connect→查→disconnect，會在同一條連線上互拆，全部等一個不會回來的回應。
  **SOP-12 只規範了「跨視窗不並行」，沒管稽核自己 session 內的並行委派**
  ——外面關得很嚴，裡面自己開了六條。
- 症狀 2 的根因：**L43 只修了一半**。L43 的教訓是「叫沒有工具的 agent 做事
  ＝逼它亂代償」，落點把工單 B 路線（SQL 型）的委派對象指名到三個具
  oracleMCP 權限的 flow；但 **A 路線（CHUNK 型）當時只寫「委派對應 flow

  教義沒列＝預設開，於是它「自己做不到、又能再轉委派」，轉圈到逾時。
  九個 ps-* subagent 全數明列 `task: false`，只有這三個漏了。
- 管理者提出的關鍵反問（直接改掉了修法）：「如果某個委派對象找不到、
  但其實另一個找得到？例如 AE 的證據可能是 peoplecode、又可能是排程。」
  ——**這推翻了「型別→agent 一對一路由」的直覺解**：硬路由會製造新的假查無
  （L26 同族：問錯對象必空，而空 ≠ 不存在）。查工具矩陣後發現真相更簡單：
  CHUNK 型有 **5 個** agent 都具 ES＋Source（任一個都取得到 chunk），
  而 `ps-ae-flow` 與 `ps-metadata-flow` **四工具全譜**（程式碼與 DB 兩面都追）
  ——AE 這種跨界情境根本不會斷。真正的死路只有三種：派到零工具的
  general／explore／scout、CHUNK 任務派到無 ES/Source 的 ps-ui-flow、
  DB 任務派到無 oracleMCP 的 peoplecode／sql／sqr-flow。
- 落點：機械化＋規則——
  1. 工單 A 路線改成**允許集合＋首選**（不是一對一硬路由），明文禁止
     general／explore／scout 與（CHUNK 型的）ps-ui-flow；手術 prompt 同步。
  2. **查無不算數，除非換過管道**：首選查無 → 改派全譜的 ps-ae-flow 或
     ps-metadata-flow 再試一次，兩個管道都查無才算查無（照搬 auditor 早有的
     二次定位紀律，補進手術路徑）。
  3. general／explore／scout 補 `task: false`。
  4. 「委派一律循序」寫進 ps-audit.md／ps-deep-research.md，SOP-12 補指向。
- 原則一：**指名派工要指名到底**——同一張工單裡有一條路線指名、另一條寫
  「對應的那個」，模糊的那條就是下一次事故。修 L43 型缺陷時要掃過**全部**
  路線，不是只修觸發當下的那一條。
- 原則二：**約束自己併發，不只約束別人**。凡是宣告「這個資源是單工」的
  規則，都要同時回答「那我自己會不會同時用它兩次」——對外的操作紀律
  管不到系統自己的扇出。
- 原則三：**路由要用「誰有那個工具」定，不要用「這是什麼型別」定**。
  型別與能力不是一對一（AE 同時是程式碼與排程）；用能力定義允許集合，
  並保留一個「全譜」對象當跨界與查無時的第二管道。
- 套用：本 commit（lint 工單／auto-loop 手術 prompt／三個內建覆寫檔／
  ps-audit／ps-deep-research／SOP-12）；既有 173 項回歸全綠。

### L67 把「顆粒度過粗」誤讀成「併發有害」——循序化把單點故障放大成全域故障（2026-08）
- 事件：L66 依「err 顯示 6 個委派、打勾亂序」判定並行是卡死主因，改成
  「委派一律循序」。**下一輪只派一個 subagent，照樣卡死、零輸出零資訊。**
  管理者的判讀推翻了 L66：上一輪真正的問題是**單一 subagent 被交付 3 個任務**
  （顆粒度過粗），不是同時有幾個在跑；而且卡死本身是**機率性的**。
- 我讀錯了什麼：從「畫面上同時列著 6 個委派」推出「它們並行造成互拆連線」。
  實際上那是**顆粒度**的表徵——一個委派涵蓋多個 A 項區間／多個任務，
  輸出量過大而卡住。**同一組現象，兩種讀法，我挑了需要更多假設的那一種**
  （互拆連線是推論；顆粒度過粗是畫面上直接看得到的）。
- 更重要的是循序化的**反效果**：subagent 卡死是機率事故（L34：抽樣事故、
  非確定性障礙），而框架**沒有委派層級的逾時**（外環只殺整個 session）。
  在這個前提下：
  · **並行** → 一個卡住只損失那一個委派，其餘照常完成，**部分進度保得住**
  · **循序** → 單點故障 ＝ **整輪停擺**
  我等於把爆炸半徑從「一個委派」放大到「整輪」。
- 落點：撤回「一律循序」，改為兩條有實測依據的約束——
  1. **一個委派只做一件事**（一個檔的一個任務）；禁止把多檔／多 A 項區間／
     多任務塞進同一個委派。這才是上一輪真正的病。
  2. **併發上限 3**——照 SOP-12 自己的實測值（3 subagent 同呼成功，再多會在
     單工 oracleMCP 上排隊逾時），不是禁止並行。
- 原則一：**在「機率性故障 ＋ 無局部逾時」的系統裡，並行是韌性手段不是風險**。
  討論要不要並行之前先問：某一路卡住時，其他路的成果保不保得住？
  沒有局部恢復機制時，循序等於把所有雞蛋放進一個籃子。
- 原則二：**兩種讀法都能解釋同一組現象時，選需要較少假設的那個**。
  「顆粒度過粗」在畫面上直接可見；「並行互拆連線」需要一層推論。
  我挑了推論那個，而且它剛好與我當時腦中的 SOP-12 印象吻合——
  **符合既有假說的解釋最容易被高估**。
- 未解：**卡死的根因仍然不明**（單一委派、零輸出、零錯誤、無提示）。
  已排除：權限提示（L60/L65）、並行互拆（本課）、零工具派工（L66）。
  下一步是找 subagent 自己的執行紀錄，而不是再猜一個原因。
- 套用：本 commit（ps-audit／ps-deep-research／SOP-12；撤回 L66 的循序條款，
  L66 其餘落點（派工指名、補鎖檔封 task）不受影響）。

### L69 值域外的判定會讓整批從計分卡蒸發——塌縮且零 FAIL 是「照做」不是「放水」（2026-08）
- 事件：索引重建後第一輪 audit，管理者回報「計分卡嚴重塌縮，且沒顯示
  FAIL，但底下系統性錯誤有正確報出 index 重建的問題」。

  · 步驟 5 的值域只有 `PASS` / `FAIL(原因)` / `UNVERIFIABLE(原因)`；
  · JSON 回報格式的 verdict 範例只有 PASS；
  · 90-audit.md 模板章節叫「## FAIL / DISPUTED / UNVERIFIABLE 明細」。
  **`stale` 在整條輸出鏈上零定義。** 模型被要求做一個計分卡沒有欄位的
  判定，又被明文禁止判 FABRICATED——那些筆數無處可放，直接消失。

  「## 系統性錯誤觀察」章節。**有位置的就寫了，沒位置的就蒸發了。**
- 這不是模型偷懶：它嚴格照規則走，是規則的值域有洞。同一個形狀在
  design review 已被記為 fatal（`待人工SQL` 在稽核端零定義）——
  **同一種洞出現第二次，代表這是類別問題不是個案**：凡是規則裡出現的
  判定字面，都必須在值域、JSON schema、報告模板三處都有落點。
- 第二個洞（外環）：lint 有 `Get-ScorecardCoverage` 專門測塌縮，但那條
  只在 `-StrictAudit`（tier 2 門）升為違規，`-CoverageOnly`（tier 1 門）
  看不到它。**tier 1 因此可以在「報告塌縮到無法回灌」的情況下覆蓋畢業**——
  塌縮屬「報告可不可裁決」（下一輪拿不拿得到工單），不是「證據精不精修」。
- 第三個洞（訊息代為推因）：塌縮訊息原本寫「範圍塌縮跡象——**稽核未全量
  重驗**」。但 `Get-ScorecardCoverage` 實際只量一件事：**記分卡那一節的內文
  有沒有出現每個 NN 檔的檔名**；「稽核跑了沒」它量不到。本案正是反例——
  管理者指出稽核**跑過所有檔案、也抓出全部檔案都有重建問題**，塌縮的成因
  是「成批問題被寫成一句彙總」。我照著那句推論回報「稽核沒跑過大部分
  檔案」，**被自己工具的措辭騙了**——而且是在管理者已經給出反證之後。
- 落點：
  1. 值域封閉：明寫「只有這三個，沒有第四種」；stale 改映射到既有值域
     （找到新 id → `FAIL(ID_RELINK)`；三管道皆無 →
     `UNVERIFIABLE(INDEX_REBUILT)`）。**不新增第四種 verdict**——新增就要
     同步改 lint、模板、計分卡三處，那正是這個洞的成因。
  2. 硬規則「計分卡逐筆落位」：Evidence 每筆佔一列，計分卡列數少於
     Evidence 筆數＝本次稽核無效。
  3. lint：記分卡塌縮在 `-CoverageOnly` 下升為違規（手動執行仍不擋，SOP-2）。
  4. mcp-tool-contracts 與 SOP-11 的 stale 說法同步改掉。
  5. 塌縮訊息改為只陳述量測（「記分卡未逐檔列出 N 個檔名」），
     並註明「成批問題寫成彙總句也會觸發」——不再代為推因。
  6. auditor 加「成批同因也要逐筆列」：整批同一原因失效時仍須逐檔逐筆
     佔列（reason 相同即可），**彙總句不得取代逐筆列**；系統性成因寫進
     「## 系統性錯誤觀察」是**補充不是替代**。
- 原則一：**規則裡的每一個判定字面，都要能指出它在輸出上的落點。**
  指不出來的判定＝指示模型產生一個沒有容器的東西，結果不是報錯，
  是安靜地不見——與 L68 的「靜默空回傳」同族。
- 原則二：**檢查訊息只准陳述它量到的事實，不准附帶推因。** 一條訊息寫
  「A（成因 B）」而它其實只量得到 A，那個 B 會被下游當事實用——本案就是
  我把 lint 的 B 當成現場觀察，反過來否定管理者的直接證據。推因寫註解、
  寫 lesson，不寫進使用者會讀的那一行。
- 套用：本 commit（ps-auditor、ps-doc-lint、mcp-tool-contracts、SOP-11）。

### L70 tier 1 的迴圈在做 tier 2 的工作——三個數字用三把不同的尺（2026-08）
- 事件：管理者回報「lint 怪怪的，手術清單 44 筆、一批 7 筆、分三批？」
- 查出三件事：
  1. **批量 7 是硬編碼**（`Select-Object -First 7`），不是參數；可調的只有
     批數 `MaxSurgeryPerCycle`（預設 3）。44 筆需要 7 批，一圈只給 3 批
     → 至少 3 圈，而圈 2／圈 3 的**前置 session 對清工單零貢獻**。
     L58 的註解自己就寫過這個病（「每修 7 筆就先燒一個稽核 session…
     其中一半是白跑的稽核」），但只把 1 批放寬到 3 批——**症狀減半，
     根因沒動**。
  2. **工單的產生完全不看 `-CoverageOnly`**：降級段在前、工單在後，而工單
     是從 `$truncatedIds`／`$missingIds`／`$leakDelegable`／`$misplacedRefRows`
     四個陣列直接印的，跟 `$violations` 無關。所以 tier 1 與 tier 2 拿到
     **同一張 44 筆清單**。
  3. **auto-loop 的手術迴圈用基礎 lint 驅動**（`$lint = Invoke-Lint`），
     而相位是用 CoverageOnly 決定的。於是一圈之內：相位一把尺、手術一把尺、
     畢業門又一把尺。
- 合起來的後果：**tier 1 會燒好幾個 session 去修 [欄位]／[證據] 型工單，
  而那些型別對應的違規全在 `$polishPatterns` 白名單內＝CoverageOnly 已判定
  不擋門。** 這與 tier 分段的設計目的（L50：tier 1 不保證回溯驗證，回溯驗證
  是 tier 2 的工作；lint 自己的註解也明寫）直接牴觸——**分段是為了讓每個
  領域先到 80 分，結果 tier 1 仍在做 100 分的活。**
- 根因型態：`MaxSurgeryPerCycle` 同時扮演**防活鎖**與**控吞吐**兩個角色，
  但防活鎖早就有更精準的機制（「本批未讓清單變短就停」）。一個旋鈕兼兩職，
  調整任一用途都會傷到另一個。
- 落點：
  1. lint：`-CoverageOnly` 時工單只出 [洩漏] 型（寫入脫軌會讓章節真的缺
     內容＝缺料）；[欄位]／[證據] 不出單，但**明講被抑制了幾筆**
     （無聲截斷會讀成「已經沒事了」）。
  2. auto-loop：手術迴圈的 lint 依 tier 換尺——tier 1 用 `-Coverage`。
  3. 批量參數化 `-SurgeryBatchSize`（預設仍 7），log 與 Preflight 明寫
     「本圈最多處理 N 筆」，不再讓人自己算。
- 原則：**同一圈裡的相位、工單、畢業門必須用同一把尺。** 尺不一致時，
  迴圈會朝著沒有人在驗收的方向努力——外環照樣顯示「有在做」，
  而它做的不是門在要求的事。
- 套用：本 commit（ps-doc-lint 工單分層、ps-auto-loop 手術迴圈換尺＋批量參數化）。

  3. 只剩人工項時 Preflight 直接顯示「**不會啟動**」，與迴圈的早停一致。
- 原則：**判斷與顯示必須讀同一份計算。** 顯示端自己重算一次，等於在系統裡
  種一個永遠不會被測到的分身——它只在「兩邊剛好不同」的那天現身，
  而那天你正在拿它做決定。
- 套用：本 commit（ps-auto-loop 抽出 Get-CoverageBreakdown，兩處共用）。

### L76 誤報把畢業擋死——lint 第二次「驗字面而不是驗事實」（2026-08）
- 事件：tier 1 只剩一項 AUDIT_ONLY 違規「記分卡未逐檔列出 5 個檔名」。
  管理者打開 `90-audit.md` 實地查看：**根本沒有塌縮，五個檔全在**——
  模型只是把檔案欄寫成「01」「02」「03」而不是 `01-TW_XXX.md`。
- 根因：`Get-ScorecardCoverage` 拿**完整 basename** 去比對記分卡內文，
  編號代稱當然比不到。**檢查驗的是字面，不是它宣稱要驗的事實**
  （「有沒有逐檔列」）。
- 這是同一個函式的**第二次**同類錯誤：上一次是綁章節標題名（模型自創
  「本輪已完成檔案總覽」取代「總覽記分卡」），已改成「以結構找表、
  不綁章節名」。改了標題那一半，檔名這一半原封不動——**當時就該問
  「這個函式還有哪裡在比字串」。**
- 為什麼是死結而不只是雜訊：L69 讓塌縮在 CoverageOnly 也擋門，於是
  誤報 → 相位 audit → audit 重寫 90-audit.md → 模型照樣寫短檔名 →
  誤報 → 相位 audit……**每一輪都在做同一件事、拿同一個結果**，
  直到「audit 相位連續 2 圈零回灌」熔斷。這正是 L23 早就寫過的
  「純命名問題＝無修復管道的畢業活鎖」，我在 L69 加門檻時沒回頭看那條。
- 落點：
  1. 覆蓋判定加**編號代稱**：完整檔名比不到時，退而接受 NN 編號，
     但**只在該編號唯一對應一個檔**時才算（`NN-X.md` 與續篇 `NN-X-2.md`
     共用前綴，一個「01」證明不了兩個都列到）。
  2. 編號必須帶**錨點**——列首／清單項／第一個儲存格開頭，或任一儲存格
     **恰為**該編號（涵蓋有流水號欄的表）。行號、日期（`2026-08-01`）、
     chunk id 裡也有兩位數，不加錨點會反向誤放行。九個情境已逐一驗過。
  3. 以編號代稱通過時**發警告不擋門**：「覆蓋算數，但完整檔名才讓
     『哪一檔沒被驗』一眼可讀」——資料在就不追殺（L23），但講出來。
  4. ps-deep-research 步驟 4 明寫：記分卡檔案欄一律寫完整檔名。
- 原則一：**一條檢查要驗的是它宣稱的那個事實，不是碰巧能比對的那個字串。**
  寫檢查時問：「這件事若以另一種合理寫法呈現，我還測得到嗎？」
- 原則二：**同一個函式犯過一次形式主義，要把整個函式重看一遍。**
  修掉眼前那一半、留下另一半，等於安排下一次同樣的當機。
- 套用：本 commit（ps-doc-lint 覆蓋判定＋警告、ps-deep-research 步驟 4）。
