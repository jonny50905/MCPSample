ARCHITECTURE ─ 系統架構

分層分工：主控不碰資料，專家各查各的，稽核員獨立驗證

主控 AI 的記憶空間很小，所以它只負責「派工與彙整」；真正的檢索由各專家 在自己的獨立空間完成，只把結論＋證據交回來。

HOW ─ 同事使用指南

四種情境，各走各的路

記住一件事就好：問問題用 PS MODE、產文件打指令。其餘都是變化。

情境 A我想問一個業務問題
1按 Tab 切到 ps-orchestrator（PS MODE）
2直接用中文問，愈具體愈好
3例：「兵役狀態有哪些選項？選了免役之後系統會做什麼？」
得到：業務語言的答案＋每個結論的證據（檔案:行號）與可信度標註
情境 B我要某領域的完整文件
1打 /ps-research 轉職（任何領域詞都行）
2它自動盤點功能清單 → 逐一深查 → 寫成文件
3中斷沒關係——重打同一指令會接著跑，不重工
得到：docs/ps-research/轉職/ 資料夾——總覽＋逐功能文件＋稽核報告
情境 C我要查資料表的內容
1按 Tab 切到 build（一般模式）
2請它查，它會直接連 Oracle
3例：「查 PS_XXX 裡 EMPLID=123 的資料」
得到：查詢結果表格。（臨機查詢請走這裡，別用 PS MODE）
情境 D它答錯了
1直接指正——它會重新查證，不會盲目附和
2確認真的錯 → 打 /ps-lesson 一句話描述 登錄教訓
3本機立即生效；PR 合併後全團隊不再犯同類錯
得到：當下的更正答案＋長期的系統改善（跨 session 記取教訓）

OPERATIONS ─ 使用守則

五條好習慣，避開絕大多數的問題

中斷不怕，重打即續進度存在「檔案」不在對話——關掉、當機、跑一半都沒關係，開新視窗重打 /ps-research 會從上次未完成處接著跑，不重工
續跑開新視窗，不叫回舊對話舊對話帶著失敗歷史會誤導模型。原則：檔案即狀態、對話即拋棄式
只唸不做就推一下模型偶爾把指令步驟唸一遍（1、2、3…）就停住不動——回一個字「做」即可踢回行動模式，不用重開視窗
卡住就喊停出現「continue after repeat failures」提示時選「拒絕」，然後跟它說：「這項標 BLOCKED，繼續下一項」
更新後要重啟git pull 拿到新版規則後，重啟 OpenCode 才會載入生效

FEEDBACK ─ 答錯了怎麼辦

糾錯流程：本機立即修正，PR 審核把關團隊生效

發現答案有誤時不用客氣——指正是讓系統變聰明的正式管道，而且有雙重安全設計： AI 不盲從你的說法、規則變更必經人審。

1. 直接指正AI 會重新查證而非附和——你說的內容也會被驗證
→
2. 確認真錯 → /ps-lesson一句話描述錯誤；AI 自動分類落點並本機立即修正（規則只加不刪、事實留作廢紀錄）
→
3. 內部 git PR修改以 PR 送審，管理者看 diff 把關；不合格退回 revert
→
4. merge → 全員 pull其他同事 pull＋重啟後，整個團隊不再犯同類錯

註：若重新查證後發現其實沒有錯，AI 會拿證據向你說明——它被規定不能為了迎合使用者而改口。 每筆教訓都記錄在 applied.md，可追溯、可回滾。

GOVERNANCE ─ 權責與安全

一般同事只要會對話；管理動作全部有 SOP

角色做什麼依據
一般使用者對話問答、產文件、跑稽核、登錄教訓——全部在 OpenCode 內完成本頁情境 A–D
管理者批准教訓套用、lint 健檢、內部 git 版控、回滾、人工修正標記SOP.md（11 份核取清單）
唯讀為預設問答模式零寫入權限；資料庫僅允許 SELECT，附列數上限與逾時保護
權限白名單每個 AI 專家只拿得到自己需要的工具，越權在物理上不可能
版控與回滾產出進「內部」git（嚴禁外部遠端），任何損壞可回滾
人在關鍵環節規則變更以內部 git PR 人審把關；檔名變更一律人工確認
KNOWLEDGE ─ Entity Wiki 知識庫

查過的知識不重查：一物一檔、連結成網、越用越聰明

深查過程中，每個核心物件（畫面、資料表、程式）都會「歸戶」成 docs/ps-research/wiki/ 裡的一個檔案。之後問答先查 wiki—— 命中已驗證的條目就直接引用，不必重新翻百萬行程式。 這套做法源自「互連知識網勝過扁平搜尋」的研究結論，落地成六條紀律：

一物一檔，檔名即身分如 wiki/TW_MILITARY_DATA.md；建檔前先查重（檔名＋別名），同一物件永遠只有一份檔案
觀察＋關聯條列事實（Observations）＋帶型別的 [[連結]]（Relations）——問答沿著連結追出完整業務脈絡
作廢不刪除事實變更寫進「Invalidated」節留下痕跡；人工蓋過 reviewed 章的檔只能追加、不能改寫
確定性檢索，不用向量index.md 目錄＋精確比對——面對精確的 ERP 物件名，比語意搜尋可靠且可驗證
寫的人 ≠ 審的人研究員 AI 寫、稽核員 AI 重新取證驗、人工蓋章——三方分立，互相制衡
lint 當編譯器欄位格式、90 天過期警示、斷鏈與孤兒檔——機器逐項健檢，壞了就亮紅燈
流程：深查完成一項 → 歸戶 wiki → 稽核驗證 → 問答 wiki-first（目錄 → 條目 → 沿連結）→ verified 條目可直接引用
APPENDIX ─ 37 個回歸測試情境

驗收清單：每一題都守著一個踩過的坑

完整定義（檢查點與評分）見 test-scenarios.md；日常快速健檢用其中 9 題的 Smoke Set。

題目多以「兵役」為題材——它出自原始需求文件的完整範例，正確答案已知才能評分。 考的是規則遵循（委派、證據、不編造），與領域無關：規矩在兵役守得住，任何領域就守得住。 要測其他領域，把題目中的物件名換成你熟悉、知道正確答案的領域即可，檢查點照用。
