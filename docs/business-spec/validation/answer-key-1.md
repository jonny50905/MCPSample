- 位置（兩邊）：

  - B 邊（員工可自行取消）：`09-business-logic.md §3 BR-09`「主管核准後至開課日前一日（含），員工可自行取消報名；取消後名額即釋出。」
  - 支持 A 邊的旁證：`04-workflow.md §3.1` 轉移表「主管核准→已取消」「已確認→已取消」兩列觸發者只有訓練承辦；`08-api.md §2` 取消 API 可呼叫角色「依 03 §2」。
  - 支持 B 邊的旁證：`05-ui.md §3.2`「取消報名」按鈕角色含員工、條件「符合 09 §3」；`01-overview.md §2.1` 第 5 列「依 09 §3」。
- 期望處理：
  - 類型：矛盾。缺什麼要寫出兩處（至少 03 §2 與 09 §3 BR-09）。
  - 暫定做法：對到「兩處說法矛盾 → 採限制較多的一邊，並寫明是哪一邊」→ 採 03 §2：核准後（主管核准、已確認）只有訓練承辦可取消，員工不能自行取消。

- 扣分情形：以多數決（03＋04＋08 對 09＋05）自行定案並標「已確認」；兩邊各寫一條「已確認」需求；暫定做法採較寬鬆的 09；只登記 03 vs 04 或漏寫其中一處。
- 不屬矛盾的部分：「取消後名額釋出」與 `09 §1 BR-03`（只有已送出、主管核准、已確認計入名額）一致，可寫成已確認的 RULE；釋出後名額給誰屬 P2。

## 3. 各類需求：期望條數與必含要點

### FLOW（5～10 條）
- 主流程：承辦開梯次 → 員工查詢並送出報名（帶入直屬主管為審核者）→ 主管核准或退回 → 核准後通知員工與承辦 → 承辦確認 → 梯次結束後承辦逐筆登錄完訓或缺席（04 §1）。
- 名額已滿時只能登記候補（04 §1 第 3 步）。
- 主管退回：報名結束、不可修改再送，要參加須重新報名（04 §2）。
- 承辦取消梯次：該梯次所有尚未結束的報名改為已取消（04 §2、09 BR-11）。
- 取消報名的路徑：核准前、核准後（核准後部分待確認，P1）。
- 主管本人報名由其直屬主管審核（03 §2 註；歸 FLOW、PERM 或 RULE 皆可，只能寫一處）。

### UI（以畫面區塊為單元約 12～20 條；以欄位、按鈕為單元約 35～50 條）
- S1 梯次查詢：查詢條件三個（課程類別預設「全部」、上課日期起預設今日、關鍵字比對課程名稱，皆非必填）；只列開放報名的梯次、依上課開始日排序；名額狀態顯示「尚餘 N 名」或「候補」；尚有名額顯示「報名」、名額已滿顯示「登記候補」；按下後開啟報名單並帶入所選梯次。
- S2 報名單：員工編號預設登入者、唯讀；姓名、部門、直屬主管由人事資料帶入、唯讀；課程／梯次帶入所選梯次、唯讀；報名理由（必填待確認，P3b；尚未送出時可改）；用餐需求（非必填、預設「一般」、尚未送出或已送出時可改、只在梯次有供餐時顯示）；報名狀態唯讀、送出或登記候補後顯示；審核意見（主管退回時必填、直屬主管在已送出時可填、送出後顯示）；承辦備註（只有訓練承辦看得到、隨時可改）。
- S2 按鈕：送出（尚未送出且尚有名額）、登記候補（尚未送出且名額已滿）、取消報名（員工、承辦；待確認，P1）、核准與退回（直屬主管、狀態為已送出）。
- S3 待審核清單：列出審核者為登入主管且狀態為已送出的報名、依送出時間排序；顯示員工姓名、部門、課程名稱、上課日期、報名理由、送出時間；可多筆一次核准；退回須逐筆填審核意見。
- S4 梯次學員管理：依狀態分組（已確認、主管核准、已送出、候補）；候補依登記時間先後排列（只是顯示排序）；確認可逐筆或多筆；梯次結束後對已確認學員選完訓或缺席，預設空白。
- S5 課程：課程代碼只在新增時可填；生效日期預設今日；課程名稱、類別、時數必填；狀態預設「有效」。
- S5 梯次：梯次編號系統依序給號、唯讀；上課起訖日、名額、報名截止日、供餐只在開放報名時可改；地點在梯次未結束時可改；名額預設 30；報名截止日預設上課開始日前 7 日；供餐預設否；梯次狀態唯讀；「取消梯次」在開放報名或報名截止時顯示，按下要再確認一次。
- 不應出現：課程費用欄（只在 SCOPE 排除）、型別、技術名。

### DATA（7～16 條）
- 課程資料依生效日期保留歷史：名稱、類別、時數等異動時新增一筆，不覆蓋；報名與出席紀錄顯示上課開始日當時有效的課程資料（07 §2，配合 05 §6.1 生效日期）。
- 課程類別選項：「專業技術」「管理職能」「法規遵循」（07 §6）。
- 課程狀態：「有效」「停用」；停用後不可再開新梯次，已開梯次不受影響（07 §6；這條歸 RULE 也可，只寫一處）。
- 梯次資料：所屬課程、梯次編號（同一課程內遞增）、上課起訖日、地點、名額、報名截止日、供餐、梯次狀態。
- 梯次狀態選項：「開放報名」「報名截止」「已結束」「已取消」。
- 報名資料：員工、梯次、審核主管（送出時帶入，之後人事異動不改）、報名狀態、報名理由、用餐需求、審核意見、承辦備註、送出或登記候補的時間（07 §4）。
- 報名狀態選項 8 個：「已送出」「候補」「主管核准」「主管退回」「已確認」「已取消」「完訓」「缺席」。
- 用餐需求選項：「一般」「素食」「不用餐」；供餐：有／無。
- 報名狀態異動紀錄：每次異動保留原狀態、新狀態、異動人、異動時間；只增不改、不可刪除（07 §5）。
- 代碼字母（A／I、T／M／C、SUB 等）可照抄引用，但不是必須，不扣分也不加分。

### RULE（13～22 條）
- 報名須於報名截止日前送出，逾期顯示「已超過報名截止日，無法報名。」（待確認，P6）
- 同一員工對同一課程同時只能有一筆有效報名（已送出、候補、主管核准、已確認），違反顯示「您已報名此課程，不可重複報名。」
- 名額計算：已送出、主管核准、已確認計入；候補不計入；達名額時只能登記候補。
- 送出時再檢查名額，多人同時報名也不得超過名額，超過顯示「本梯次名額已滿，請改登記候補。」（只取業務意義，P7）
- 審核者為送出當時人事資料中的直屬主管（可與 DATA 審核主管合併；掛 P5）。
- 主管退回時審核意見必填，未填顯示「退回時請填寫審核意見。」
- 訓練承辦只能確認狀態為主管核准的報名。
- 主管核准前員工可自行取消本人報名。
- 主管核准後至開課日前一日（含）員工可自行取消、名額釋出（待確認，P1）。
- 開課日當天起任何人都不可取消，顯示「已開課，無法取消報名。」；未到課者由承辦登錄缺席。
- 承辦取消梯次時，該梯次所有尚未結束的報名改為已取消。
- 報名截止日不得晚於上課開始日，違反顯示「報名截止日不得晚於上課開始日。」
- 名額不得調降至低於目前計入名額的人數，違反顯示「名額不得少於目前已報名人數。」
- 開課前 3 日的自動處理（待確認，P4；或改以 OTHER 掛假設）。
- 出席時數達課程時數 80% 以上為完訓，未達為缺席（待確認，P3a）。
- 缺席者自梯次結束日起半年內不得報名同一課程（待確認，P3a）。
- 必填欄位未填顯示「請填寫必填欄位。」；送出成功顯示「報名已送出，等待主管審核。」；登記候補成功顯示「名額已滿，已為您登記候補。」（可併入相關規則）。
- 訊息文字一律照抄並用「」框起。

### STATE（以狀態為單元約 6～10 條；以轉移為單元約 15～25 條）
- 報名狀態 8 個（來源 04 §3、07 §6）。
- 送出 → 已送出（員工，尚有名額）；登記候補 → 候補（員工，名額已滿）。
- 已送出 → 主管核准、已送出 → 主管退回（直屬主管；退回須填審核意見）。
- 已送出 → 已取消、候補 → 已取消（員工本人、訓練承辦）。
- 候補 → 已送出「遞補」（待確認，P2）。
- 主管核准 → 已確認（訓練承辦）。
- 主管核准 → 已取消、已確認 → 已取消（訓練承辦，開課日前一日（含）以前；員工可否待確認，P1）。
- 已確認 → 完訓、已確認 → 缺席（訓練承辦，梯次結束後）。
- 禁止：主管退回、已取消、完訓、缺席為終止狀態不可再變更；未經主管核准不可確認；候補不可直接核准或確認。
- 梯次狀態：建立時為開放報名；依報名截止日自動轉為報名截止（時點掛 P6 時待確認）；依上課結束日自動轉為已結束；承辦取消梯次 → 已取消。

### PERM（5～14 條）
- 查詢開放報名梯次、報名／登記候補（本人）：員工、直屬主管、訓練承辦都可以。
- 取消（主管核准前）：員工限本人、訓練承辦可以；直屬主管不可以。
- 取消（主管核准後）：只有訓練承辦（待確認，P1）。
- 核准／退回：只有直屬主管，限直屬部屬。
- 確認報名、登錄出席結果、課程與梯次維護、取消梯次：只有訓練承辦。
- 資料範圍：員工看本人；直屬主管看本人與直屬部屬，不含部屬的部屬；訓練承辦看全部。
- 承辦備註只有訓練承辦看得到（歸 UI 也可，只寫一處）。
- 不應出現：系統角色代碼、API 權限檢查。

### EXT（2～5 條）
- 人事資料：開啟報名單時帶出姓名、部門、直屬主管；送出時再取一次直屬主管作為審核主管（08 §3.1）。待確認，掛 P5。
- 取不到主管時的業務處理：來源未涵蓋（可獨立一條待確認，或只寫在上一條與假設裡）。
- 郵件通知：主管核准 → 通知員工與訓練承辦；退回 → 通知員工；內容含課程名稱、上課日期、審核結果、審核意見；寄送失敗不影響報名狀態（08 §3.2、04 §1 第 5 步）。已確認。
- 不應出現：呼叫路徑、回傳欄位名、範本代碼、逾時與重試。

### ACC
- 來源照用 4 條：UAT-01～UAT-04（衍生＝否；來源 `14-testing.md §2`）。UAT-01、UAT-03、UAT-04 應為已確認；UAT-02 的來源需求若掛了 P2 則待確認，否則已確認。
- 衍生條數隨規範 9.1 衍生表與各類粒度變動，照目前的衍生表可能上百條；不以條數評分，改抽查：
  1. 衍生 ACC 的衍生欄＝是，來源需求鍵只有一個。
  2. 來源需求是待確認時，衍生 ACC 也是待確認，並帶同樣的假設；預期結果依暫定做法寫。
  3. 有【邊界】情境：截止日當天（依 P6 暫定做法）、開課日前一日取消、名額剛好額滿。
  4. EXT【失敗】情境：取不到直屬主管（待確認，依 P5 暫定做法）；郵件寄送失敗（報名狀態不變，已確認）。
  5. 來源已有情境的路徑不重複衍生（例：退回未填意見已由 UAT-03 驗證）。
  6. 不把 `14 §3` 效能測試寫成 ACC。
- 三份產出的衍生條數相差超過一倍時，回饋規範：衍生表需要上限或更明確的單元。

### OTHER（0～2 條）
- 只在 P4 或其他找不到需求可掛的假設改掛 OTHER 時出現，確認狀態待確認。
