# 職缺管理（JO）業務需求文件：示範

用 `../standard.md`（業務需求文件撰寫規範，含第 10 章證據）產出的一份完整示範。**資料全部是合成的**：依職缺管理的一般概念撰寫，
物件名稱一律是示範名（`TW_DEMO_JO*`、`TW_DJO_*`），不是任何公司的實際系統，也不代表 PeopleSoft 實際行為的完整描述。

| 位置 | 內容 |
|---|---|
| `source/` | 合成來源：`status.md`（狀態圖）、`project.md`（業務名稱、目標、範圍）、`research/01`、`research/02`（研究文件：欄位、規則、權限、流程、介面、驗收情境）。刻意留了矛盾、缺漏、待確認、邊界不清、混入系統設計等缺口 |
| `out/` | Sonnet 照規範寫出的業務需求文件，一章一檔，入口 `out/README.md`；`out/10-evidence.md` 是證據章 |
| `sample-full.md` | 把 `out/` 各章依序接起來的全文，方便一次閱讀 |

怎麼產生的：Opus 寫合成來源 → Sonnet 只讀規範與來源、照「寫作順序」寫完並做完成前自我檢查（補查：不可用，所以缺口都登成假設）→
以外環同一套檢查（`scripts/ps-bizspec-lib.ps1` 的 `Invoke-PsBzCheck`：證據逐字比對、引用、表頭、必要檔）驗收，0 項問題。

看的重點：
- 每條需求的「證據」欄是 `E-###`，對到 `out/10-evidence.md` 的位置與原文摘錄；摘錄都能在 `source/` 的那一行逐字找到。
- 技術名稱只出現在證據章的摘錄，需求描述只用畫面標籤與業務用語。
- 來源的缺口都在 `out/07-assumptions.md`：矛盾（誰能暫停）、缺漏（補足後誰關閉、未列出的轉移）、未完成（薪資範圍是否必填、代理人）、看不懂（14 天內含不含第 14 天）。
