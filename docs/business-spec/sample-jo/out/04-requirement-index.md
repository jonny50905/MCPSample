# 4 從 Spec 整理業務需求

## 4.1 需求單元與需求鍵
一條需求是一條可被業務人員獨立確認對錯的業務陳述。
一句話裡有兩件可以分別對錯的事，拆成兩條；條件與它的結果、訊息是同一件事，不拆。
同一件事在來源多處出現，寫成一條需求，證據欄列出各處的證據編號；各處寫法矛盾時仍寫一條，並登記假設。
需求鍵格式為 `<類別碼>-<三位序號>`，例 `RULE-007`，只用 ASCII。序號在各類別內從 001 起依序給號；已跳號就照實保留，不補號、不改號。
需求鍵在完整內容所在章給號：SCOPE 在 3.3，ACC 在 9.1，OTHER 在 5.8，其餘在 5.1～5.7；需求索引不另給號。
來源 Spec 自己的編號只出現在第 10 章的證據，不當需求鍵。
需求鍵一經發布不改、不重用。刪除的需求保留列，確認狀態改「排除」，並註明原因。

## 4.2 需求分類
| 類別碼 | 類別 | 寫什麼 | 完整內容寫在 |
|---|---|---|---|
| SCOPE | 範圍 | 本期包含／依賴／排除哪些功能、物件或欄位 | 3.3 |
| FLOW | 流程與業務情境 | 誰在什麼時機做什麼；正常與例外路徑 | 5.1 |
| UI | 畫面與欄位 | 使用者看到什麼、能做什麼；必填、預設、可改／唯讀條件、出現／隱藏條件 | 5.2 |
| DATA | 業務資料 | 有哪些業務資料、意義、代碼值與選項、是否保留歷史 | 5.3 |
| RULE | 業務規則 | 條件 → 結果；錯誤或提示訊息 | 5.4 |
| STATE | 狀態與生命週期 | 狀態、轉移、誰能觸發、禁止的轉移 | 5.5 |
| PERM | 角色與權限 | 誰能看／改什麼、能看到哪些範圍的資料 | 5.6 |
| EXT | 與其他系統的往來 | 交換什麼、什麼時機、失敗時業務上怎麼處理 | 5.7 |
| ACC | 驗收情境 | 給業務人員操作驗證的情境 | 9.1 |
| OTHER | 其他 | 不屬於以上的業務需求 | 5.8 |
一條需求只歸一類。各類的細部界線以第 5 章為準；第 5 章沒說明時，照下列順序，第一個符合的就是它的類別：
1. 講本期做不做 → SCOPE；2. 講驗收時怎麼操作驗證 → ACC；3. 講兩個以上步驟的先後 → FLOW；
4. 講狀態的進入、離開、誰能觸發 → STATE；5. 講誰能看、能改、能看到哪些範圍的資料 → PERM；
6. 講與其他系統交換什麼 → EXT；7. 講條件成立時的結果或訊息 → RULE；8. 講畫面上看到、能操作什麼 → UI；
9. 講資料的意義、代碼值、是否保留歷史 → DATA；10. 以上都不是 → OTHER。
