# 4 從 Spec 整理業務需求

## 4.1 需求單元與需求鍵
一條需求是一條可被業務人員獨立確認對錯的業務陳述。
一句話裡有兩件可以分別對錯的事，拆成兩條；條件與它的結果、訊息是同一件事，不拆。
同一件事在來源多處出現，寫成一條需求，證據欄列出各處的證據編號；各處寫法矛盾時仍寫一條，並登記假設。
需求鍵格式為 `<類別碼>-<三位序號>`，例 `RULE-007`，只用 ASCII。序號在各類別內從 001 起依序給號；已跳號就照實保留，不補號、不改號。
需求鍵在完整內容所在章給號：SCOPE 在 3.3，ACC 在 9.1，OTHER 在 5.8，其餘在 5.1～5.7；需求索引不另給號。
來源 Spec 自己的編號只出現在第 10 章的證據，不當需求鍵。
需求鍵一經發布不改、不重用。刪除的需求保留列，確認狀態改「排除」，並註明原因。

## 4.2 需求分類
| 類別碼 | 類別 | 寫什麼 | 完整內容寫在 |
|---|---|---|---|
| SCOPE | 範圍 | 本期包含／依賴／排除哪些功能、物件或欄位 | 3.3 |
| FLOW | 流程與業務情境 | 誰在什麼時機做什麼；正常與例外路徑 | 5.1 |
| UI | 畫面與欄位 | 使用者看到什麼、能做什麼；必填、預設、可改／唯讀條件、出現／隱藏條件 | 5.2 |
| DATA | 業務資料 | 有哪些業務資料、意義、代碼值與選項、是否保留歷史 | 5.3 |
| RULE | 業務規則 | 條件 → 結果；錯誤或提示訊息 | 5.4 |
| STATE | 狀態與生命週期 | 狀態、轉移、誰能觸發、禁止的轉移 | 5.5 |
| PERM | 角色與權限 | 誰能看／改什麼、能看到哪些範圍的資料 | 5.6 |
| EXT | 與其他系統的往來 | 交換什麼、什麼時機、失敗時業務上怎麼處理 | 5.7 |
| ACC | 驗收情境 | 給業務人員操作驗證的情境 | 9.1 |
| OTHER | 其他 | 不屬於以上的業務需求 | 5.8 |
一條需求只歸一類。各類的細部界線以第 5 章為準；第 5 章沒說明時，照下列順序，第一個符合的就是它的類別：
1. 講本期做不做 → SCOPE；2. 講驗收時怎麼操作驗證 → ACC；3. 講兩個以上步驟的先後 → FLOW；
4. 講狀態的進入、離開、誰能觸發 → STATE；5. 講誰能看、能改、能看到哪些範圍的資料 → PERM；
6. 講與其他系統交換什麼 → EXT；7. 講條件成立時的結果或訊息 → RULE；8. 講畫面上看到、能操作什麼 → UI；
9. 講資料的意義、代碼值、是否保留歷史 → DATA；10. 以上都不是 → OTHER。

# 5.1 流程與業務情境

本檔列出流程與業務情境需求 9 條（待確認 1 條、排除 0 條）。來源：research/01-job-opening-create.md、research/02-job-opening-approval.md。假設見 `07-assumptions.md`。

### 職缺送審與核准
#### FLOW-001 職缺送審與核准
- 描述：招募人員或用人主管建立職缺並送審，第一層核准者核准後職缺開放徵才，並通知招募人員與用人主管。
- 路徑類型：正常
- 觸發：招募人員或用人主管需要開缺時
- 角色：招募人員、用人主管、上層主管
- 步驟：1. 招募人員或用人主管建立職缺 → STATE-009、STATE-010 2. 建立者選擇職位並填寫職缺資料 → EXT-001 3. 建立者按「送審」 → STATE-011 4. 取得用人主管的直屬主管作為第一層核准者，並通知第一層核准者 → EXT-002、EXT-005 5. 第一層核准者核准（核准層級見 RULE-010） → STATE-013 6. 通知招募人員與用人主管 → EXT-008
- 結束：職缺為「已核准」，開放徵才
- 證據：E-092、E-093、E-094、E-095、E-015、E-097、E-096／確認狀態：已確認／相關假設：—
#### FLOW-002 兩層核准
- 描述：開缺人數 6 人以上時，第一層核准後送人資主管做第二層核准，核准後回到 FLOW-001 第 6 步。
- 路徑類型：例外（分出自 FLOW-001 第 5 步）
- 觸發：開缺人數 6 人以上（含 6 人）的職缺，第一層核准者核准時
- 角色：上層主管、人資主管
- 步驟：1. 第一層核准者核准，職缺仍為「待核准」（見 RULE-011） 2. 通知人資主管待審 → EXT-006 3. 人資主管核准 → STATE-014
- 結束：職缺為「已核准」，回到 FLOW-001 第 6 步
- 證據：E-034、E-081／確認狀態：已確認／相關假設：—
#### FLOW-003 退回後重新送審
- 描述：核准者退回後，建立者依退回原因修改再送審，從第一層重新核准，回到 FLOW-001 第 4 步。
- 路徑類型：例外（分出自 FLOW-001 第 5 步）
- 觸發：核准者（任一層）退回職缺時
- 角色：核准者、建立者
- 步驟：1. 核准者按「退回」 → STATE-015 2. 通知建立者退回原因 → EXT-007 3. 建立者依退回原因修改後再按「送審」，重新送審的次數不限 → STATE-016
- 結束：職缺為「待核准」，回到 FLOW-001 第 4 步，從第一層重新核准
- 證據：E-060、E-062、E-046／確認狀態：已確認／相關假設：—
#### FLOW-004 取消草稿職缺
- 描述：建立者在職缺尚未送審時取消職缺，職缺在此結束。
- 路徑類型：例外（分出自 FLOW-001 第 1 步）
- 觸發：建立者要取消「草稿」狀態的職缺時
- 角色：建立者
- 步驟：1. 建立者按「取消職缺」，畫面顯示「確定要取消這個職缺嗎？」，按「是」 → STATE-012
- 結束：職缺為「已取消」
- 證據：E-056、E-098、E-055／確認狀態：已確認／相關假設：—
#### FLOW-005 取消已退回職缺
- 描述：建立者在職缺被退回後不再修改而取消職缺，職缺在此結束。
- 路徑類型：例外（分出自 FLOW-003 第 2 步）
- 觸發：建立者要取消「已退回」狀態的職缺時
- 角色：建立者

### 暫停與恢復
#### FLOW-006 暫停並恢復徵才

### 補足
#### FLOW-008 已錄取人數補足職缺
- 描述：錄用作業每錄用一人回寫已錄取人數，人數達到開缺人數時職缺自動變為已補足，並通知招募人員與用人主管。

- 結束：職缺為「已補足」
- 證據：E-102、E-103、E-040、E-070／確認狀態：已確認／相關假設：—

- 路徑類型：正常

- 證據：E-091、E-101、E-023、E-050／確認狀態：已確認／相關假設：—

## 6.2 狀態值
確認狀態只有下列 5 個值：

| 值 | 意思 | 誰能設 | 怎麼設 |
|---|---|---|---|
| 待確認 | 內容還不能當定案：來源標為草稿、缺證據，或有開放的假設 | 文件整理者（初寫、7.1 發現缺口、8.2 重新確認）；人 | 在追蹤表改；同步 04 與該需求完整內容所在的檔 |
| 已確認 | 內容清楚，且沒有開放的假設影響它 | 文件整理者（初寫：來源標示已確認或沒有標示，且內容清楚）；業務窗口（人工確認） | 同上；人工確認要填確認人／日期 |
| 已交付 | 這條需求已做進成品 | 只有人 | 只改追蹤表 |
| 已驗收 | 業務人員實際操作後通過（9.2 有紀錄） | 只有人 | 只改追蹤表，並填驗收結果、驗收日期 |
| 排除 | 來源標為排除，或需求因 Spec 改版刪除 | 文件整理者（來源標排除；8.2 的刪除） | 同「待確認」；備註寫原因，保留該列 |

- 允許的轉移：待確認 → 已確認 → 已交付 → 已驗收；任一值 → 排除；已確認、已交付、已驗收 → 待確認（只因為重開假設或 8.2 重新確認）。其他轉移不做。
- 文件整理者只設 `待確認`、`已確認`、`排除`；`已交付`、`已驗收` 只由人設定，整理者不改。
- 確認狀態改成 `待確認`、`已確認`、`排除` 時，追蹤表、04 索引、該需求完整內容所在檔三處同改。`已交付`、`已驗收` 只在追蹤表；04 與完整內容所在檔是 `已確認` 時，追蹤表可以是 `已確認`、`已交付`、`已驗收`。

# 7 缺口、矛盾與假設

## 7.1 什麼算缺口
對每個疑點依序問，第一個符合的就是它的類型：
| 順序 | 類型 | 判斷規則 | 例 |
|---|---|---|---|
| 1 | 矛盾 | 兩處（含同檔兩節）對同一件事的說法不能同時成立 | 一處寫借用期間最長 7 天，另一處寫 14 天 |
| 2 | 未完成 | 來源自己標示草稿、待補、待確認、TBD，或內容是佔位（「略」「同上」但上面沒有） | 規則表「逾期處理」格寫「待補」 |
| 3 | 看不懂 | 讀完仍無法用一句話講出「誰、在什麼條件下、得到什麼結果」，或用了來源沒定義的代碼或縮寫 | 「類型 B 走簡易流程」，沒說類型 B 是什麼 |
| 4 | 缺漏 | 來源提到一件事，但少了第 5 章標「必答」的欄位，或少了寫需求必要的一項（條件、結果、角色、代碼值、訊息） | 寫「逾期要通知」，沒寫通知誰 |

不算缺口：
- 兩處說法可以同時成立（一般規則加例外）→ 兩條都寫成需求。
- 來源明說「本期不做」「不適用」→ 寫成 SCOPE 排除。
- 只涉及系統設計的疑問（資料怎麼存、怎麼實作）→ 不登記。
- 第 5 章非必答欄填 `—`（來源沒提）→ 不登記。

每筆假設至少掛一個需求鍵。找不到現有需求可掛 → 在 5.8 末尾「其他」開一條 OTHER 需求。

# 8 Spec 改版

## 8.1 新版與前一版並存
目前來源版本：來源未標示；取得日期：2026-11-03；位置：`docs/business-spec/sample-jo/source`。
來源 Spec 出新版時，前一版留在原處，不刪、不改。新版放在另一個資料夾 `docs/business-spec/sample-jo/source-〈新版本〉`。
業務需求文件只有一份，在 `docs/business-spec/sample-jo/out` 就地更新，不另存新資料夾。
每次改版在本檔「Spec 差異報告」追加一段，標明新版與前一版的版本與日期，不覆蓋舊段。

## 8.2 差異處理
改版依下列順序處理：
1. 差異比對：逐檔比對新版與前一版（標題、表格列、代碼值、訊息文字），每個差異列成「Spec 差異報告」一列，類型只有新增、修改、刪除。
2. 需求鍵增刪改：新增 → 新需求鍵（該類別續號）；修改 → 改寫原需求的描述與來源，需求鍵不變；刪除 → 該列保留，確認狀態改「排除」，備註寫「Spec 〈版本〉已刪除」。
3. 影響評估：找出引用被改需求鍵的 FLOW，以及「來源需求鍵」含該鍵的 ACC，填入差異報告「影響的情境與驗收」。
4. 重新確認：受影響的需求（含其 ACC）確認狀態一律改回「待確認」；追蹤表的驗收結果與驗收日期改 `—`，備註寫「Spec 〈版本〉修改，需重新確認」。
5. 同步：更新 04 索引、追蹤表、07 假設（新版已補的依 7.4 關閉；新版新出現的缺口登記新 A-###）、9.1 的衍生情境，最後更新 8.1 的目前來源版本、2.4 與 README 文件資訊的「根據的來源 Spec 版本」。

Spec 差異報告：
| 項次 | 來源位置 | 類型 | 舊內容摘要 | 新內容摘要 | 影響的需求鍵 | 處理 | 影響的情境與驗收 |
|---|---|---|---|---|---|---|---|
（尚無改版）

## 8.3 需求鍵穩定性
需求鍵發布後不改、不重用。刪除的需求保留原列，確認狀態改「排除」並寫原因。假設編號 A-### 同樣不改、不重用。

通過標準（三項都成立才填 `通過`）：
1. 操作人是業務人員，不是開發者，也不是文件整理者。
2. 照該 ACC 的前置條件與操作步驟做。
3. 實際結果在業務上看得到的部分，與預期結果逐句一致。

任一項不成立填 `未通過`，差異說明寫哪裡不同；「後續處理」只有三個值：`修正成品`（需求寫對、做錯）、`新增假設`（需求本身缺或錯，回 7.2 登記）、`無`。

## 9.3 本期完成判定
本期完成要同時成立：
1. 9.1 的每個 ACC 在 9.2 都有「通過」的最新紀錄。
2. 07 的 7.2 沒有狀態「開放」的假設。
3. 追蹤表中確認狀態不是「排除」的需求：被任一 ACC 的來源需求鍵引用的，都是「已驗收」；沒有被引用的（例如範圍、業務資料），都是「已交付」或「已驗收」。
4. 第 1 章 1.2 的四項成功指標都成立。

## 9.4 審閱通過不等於驗收通過
「來源 Spec 審閱通過」只表示來源 Spec 的內容被審閱過，不等於業務驗收通過。本文件寫完或自我檢查通過，同樣不等於業務驗收通過。業務驗收只以 9.2 的紀錄為準。

## A 名詞表
| 名詞 | 意思 |
|---|---|
| 來源 Spec | 輸入的 Spec 檔案，放在 `docs/business-spec/sample-jo/source`。唯讀，是唯一業務真相 |
| 業務需求文件 | 依本規範寫出的產出，放在 `docs/business-spec/sample-jo/out` |
| 需求 | 業務需求文件中有需求鍵的一條業務陳述 |
| 需求鍵 | 需求的穩定編號，格式 `<類別碼>-<三位序號>`，例 `RULE-007` |
| 類別碼 | SCOPE、FLOW、UI、DATA、RULE、STATE、PERM、EXT、ACC、OTHER，共 10 個 |
| 假設 | 來源缺漏、矛盾、未完成、看不懂時登記的待解事項，編號 `A-###` |
| 暫定做法 | 假設未關閉前，需求暫時採用的最保守做法 |
| 業務窗口 | 能拍板業務問題的人（代稱，不寫真名） |
| Spec 產製端 | 產出來源 Spec 的人或流程，能回頭補查舊系統 |
| 確認狀態 | 待確認、已確認、已交付、已驗收、排除，見 6.2 |
| 驗收情境 | 給業務人員操作驗證的情境，需求鍵類別 ACC |
| 衍生 | 來源沒有直接寫、但由其他需求機械推出的項目，目前只用於驗收情境；必須寫來源需求鍵 |
| 證據 | 支持一條需求或一筆假設的一段來源原文，編號 `E-###`，見第 10 章 |
| 補查 | 來源檔案不足以支持時，由外環向舊系統查詢；結果檔在 `evidence/`，只有「結果」節能當證據 |
