# 業務需求文件撰寫規範

你要把一組「來源 Spec」整理成一份「業務需求文件」：只談業務需求，不談系統設計。
讀者是業務窗口、業務驗收人員，以及之後依這份文件做系統的團隊。照本規範逐章寫，每一章的格式、字樣與判斷規則都以本規範為準。

## 怎麼開始與續寫

- 使用者會告訴你兩個位置：`<來源資料夾>`（來源 Spec，唯讀）與 `<輸出資料夾>`（業務需求文件）。少了任一個就先問，不要猜。
- `<來源資料夾>` 裡只讀得到文字檔（`.md`、`.txt`、`.csv`、`.json`）。有 Word、Excel、PDF、圖檔時，先列出檔名並停下，請使用者轉成文字檔再放進來；不要自己寫轉檔程式。
- **新寫**：`<輸出資料夾>` 沒有 `progress.md` → 從「寫作順序」第 1 步開始。
- **續寫**：有 `progress.md` → 讀它，從第一個沒打勾的項目接續；已打勾的檔照「已打勾的檔怎麼改」處理，不重寫。
- **改版**：使用者說來源 Spec 出了新版 → 照第 8 章 8.2 處理。
- 讀規範：開始時讀本規範「通用規則」；每寫一章前，再讀本規範該章那一節。

## 通用規則

### 名詞（全文統一，不換說法）

| 名詞 | 意思 |
|---|---|
| 來源 Spec | 輸入的 Spec 檔案，放在 `<來源資料夾>`。唯讀，是唯一業務真相。格式不固定 |
| 業務需求文件 | 你依本規範寫出的產出，放在 `<輸出資料夾>` |
| 需求 | 業務需求文件中有需求鍵的一條業務陳述 |
| 需求鍵 | 需求的穩定編號，見「需求鍵與類別碼」 |
| 假設 | 來源 Spec 缺漏、矛盾、未完成、看不懂時登記的一筆待解事項，編號 `A-###` |
| 業務窗口 | 能拍板業務問題的人（代稱，不寫真名） |
| Spec 產製端 | 產出來源 Spec 的人或流程，能回頭補查舊系統 |
| 衍生 | 來源沒有直接寫、但由其他需求機械推出的項目；只用於驗收情境，必須寫出來源需求鍵 |

- 每個輸出檔第一行是檔頭 `# 〈章節號〉 〈標題〉`，例 `# 3 怎麼讀 Spec`、`# 5.4 業務規則`；章內各節用 `## 〈節號〉 〈節標題〉`，例 `## 3.3 範圍判讀`。README.md 的檔頭見第 0 章。
- 每次寫檔不超過 150 行；超過就拆續檔 `<檔名去 .md>-02.md`、`-03.md`。續檔檔頭在原檔頭後加「（續 02）」，表格在續檔重寫表頭，主檔末尾列出各續檔。

### 需求鍵與類別碼

- 格式 `<類別碼>-<三位序號>`，例 `RULE-007`，只用 ASCII。序號在各類別內從 001 起依序給號；已經跳號就照實保留，不補號、不改號。
- 來源 Spec 自己的編號寫在「來源」欄，不拿來當需求鍵。
- 需求鍵一經發布不改、不重用；刪除的需求保留列，確認狀態改「排除」並註明原因。

| 類別碼 | 類別 | 寫什麼 | 完整內容寫在 |
|---|---|---|---|
| SCOPE | 範圍 | 本期包含／依賴／排除哪些功能、物件或欄位 | 3.3 |
| FLOW | 流程與業務情境 | 誰在什麼時機做什麼；正常與例外路徑 | 5.1 |
| UI | 畫面與欄位 | 使用者看到什麼、能做什麼；必填、預設、可改／唯讀條件、出現／隱藏條件 | 5.2 |
| DATA | 業務資料 | 有哪些業務資料、意義、代碼值與選項、是否保留歷史 | 5.3 |
| RULE | 業務規則 | 條件 → 結果；錯誤或提示訊息 | 5.4 |
| STATE | 狀態與生命週期 | 狀態、轉移、誰能觸發、禁止的轉移 | 5.5 |
| PERM | 角色與權限 | 誰能看／改什麼、能看到哪些範圍的資料 | 5.6 |
| EXT | 與其他系統的往來 | 交換什麼、什麼時機、失敗時業務上怎麼處理 | 5.7 |
| ACC | 驗收情境 | 給業務人員操作驗證的情境 | 9.1 |
| OTHER | 其他 | 不屬於以上的業務需求 | 5.8 末尾 |

- 每條需求只在「完整內容寫在」那一處寫完整內容；需求索引（4.3）與追蹤表（6.1）只寫一行摘要。
- 同一件事該歸哪一類，以第 5 章「歸屬類別」表為準。
- 來源標為本期排除的功能、物件或欄位，只在 3.3 寫一條 SCOPE（範圍類型「排除」），第 5 章不另立需求、不展開細項。

### 固定表頭（跨章共用，照抄，不增減欄、不改欄名與欄序）

- 範圍（3.3）：`| 需求鍵 | 範圍類型 | 項目 | 描述 | 來源 | 確認狀態 | 相關假設 |`
- 需求索引（4.3）：`| 需求鍵 | 類別 | 摘要 | 來源 | 確認狀態 | 相關假設 |`
- 追蹤表（6.1）：`| 需求鍵 | 摘要 | 確認狀態 | 確認人／日期 | 驗收結果 | 驗收日期 | 備註 |`
- 假設（7.2）：`| 編號 | 類型 | 缺什麼 | 暫定做法 | 影響的需求鍵 | 該問誰 | 狀態 | 關閉依據 |`
- 問題清單對照（7.3）：`| 來源問題 | 對應假設或答案位置 | 說明 |`
- 驗收情境（9.1）：`| 需求鍵 | 情境 | 前置條件 | 操作步驟 | 預期結果 | 來源需求鍵 | 衍生 | 來源 | 確認狀態 | 相關假設 |`
- 第 5 章各類的表頭見第 5 章各節。每條需求都有：需求鍵、描述（或摘要）、來源、確認狀態、相關假設。
- 「相關假設」欄寫 `A-###`，多個用頓號分開；沒有就寫 `—`。
- 摘要一句，不超過 40 字，不含技術名稱與「|」。

### 欄位值的字樣（只用這幾種，不自創）

| 字樣 | 用在 |
|---|---|
| 照寫來源的內容 | 來源有寫 |
| `無` | 來源明寫「沒有」「不限」「不適用」 |
| `—` | 來源沒提，而且這欄不是「必答」；或本規範指定填 `—` 的欄 |
| `來源未涵蓋` | 業務內容找不到，而且這欄是「必答」（第 5 章各節標示），或本規範指定的位置；一定要登記假設 |
| `〈待填〉` | 由人補的文件資訊（擁有者、版本、日期等）；不登記假設 |

- 本規範標「固定文字」的引用區塊：照抄區塊裡的文字，寫成一般段落，不含開頭的「>」；〈 〉 空格要填。

### 來源標示

- 每條需求、每筆假設都要有來源：`<檔名> §<章節或標題>`，必要時加表格列或項次，例 `05-ui.md §3.2 第 4 列`。同一件事在多處出現，用頓號列出各處。
- 用業務語言改寫；只有訊息文字、畫面標籤、代碼值、狀態名稱這類**原文本身就是需求**的東西照抄原文，用「」框起。
- 技術名稱（資料表名、欄位技術名、程式名、端點）只能出現在「來源」欄當定位，寫法 `<檔名> §<章節>（原名 〈技術名〉）`；不寫進描述或摘要。

### 確認狀態

值只有 `待確認`／`已確認`／`已交付`／`已驗收`／`排除`（定義見第 6 章 6.2）。你初寫時只用 `待確認`、`已確認`、`排除`：

- 來源標為本期排除 → `排除`（只出現在 3.3，以及因改版刪除的需求）。
- 有開放的假設影響這條需求 → `待確認`。
- 其餘：來源標示已確認或沒有標示，而且內容清楚 → `已確認`。
- **`待確認` 與開放假設一定成對**：確認狀態是 `待確認` 的需求，相關假設一定指向至少一筆開放假設；相關假設指向開放假設的需求，確認狀態一定是 `待確認`。
- 來源把一段標為草稿、待確認、待補、未定（見 2.3）→ 每段登記一筆假設（類型「未完成」），這段整理出的需求都掛這一筆。

### 假設

- 欄位與填法見第 7 章 7.2；什麼算缺口見 7.1；暫定做法照 7.2 的「暫定做法表」，不自創。
- 同一來源段落、同一個缺項的多條需求，合併登記一筆假設，「影響的需求鍵」全列。
- 寫作順序第 3～9 步時一發現假設，就給下一個 `A-###`（從 A-001 起，全文件唯一、依序給號），立刻追加到 `07-assumptions.md` 的 7.2 表（檔還沒有就先建檔頭、節標題與表頭），並把它填進受影響需求的「相關假設」欄、確認狀態改 `待確認`。

### 禁止（全規範、全產出適用）

- **不寫系統設計**：資料表、欄位型別與長度、主鍵、索引、API、端點、程式、類別、模組、架構、技術棧、框架、資料庫、檔案或訊息格式、效能、部署、自動化測試、實作工作項。
  來源若有這類章節，只萃取其中可確認的**業務意義**（例：「某資料要保留每次異動的歷史」「某代碼值的意思」「核准後要通知誰」），寫進對應類別；其餘不寫。
- **不編造、不推定**：來源沒寫的業務行為不寫成需求；不用「舊系統一般的做法」「業界慣例」補；改登記假設。
- 不改來源 Spec 的檔名與原文；不對來源品質下評語。
- 不寫專案時程、人力、預算、負責人指派。

5. `09-acceptance.md`（ACC 需求在 9.1 給號）

### 寫作節奏（每次回應要小）

- 開始前只讀來源的入口檔（若有）與各檔標題，先寫 `progress.md`；不要一開始就精讀全部來源。
- 一次處理一個勾選項：只讀這一項需要的來源段落 → 寫該檔 → 在 `progress.md` 打勾。
- 寫完不要再讀回檢查；全部寫完才做一次「完成前自我檢查」。寫後面的章需要用到前面自己寫的檔時，可以讀。
- 對話回覆只說做完哪一項、下一項是什麼，不把檔案內容貼回對話。

### 已打勾的檔怎麼改

已打勾的檔不重寫。只允許下列改動：
- 在表末或檔末追加列：2.3 追加新出現的狀態標記、7.2 追加假設、4.4 補列需求、預留需求鍵的列。
- 改既有列的「確認狀態」「相關假設」欄（因為登記或關閉假設）。
- 改 5 章各檔開頭固定文字裡的條數。
- 完成前自我檢查指定的修正。

### `progress.md` 格式

```markdown
# 進度

輸出：<輸出資料夾>

- [ ] 03-reading-guide.md
（照「寫作順序」第 2～10 步的檔，一檔一項，續檔不另列；最後加一項「- [ ] 完成前自我檢查」）

## 預留需求鍵
| 需求鍵 | 摘要 | 來源 | 被誰引用 |
|---|---|---|---|

## 待歸類
- （OTHER 候選：一句摘要＋來源；寫 5.8 時處理，處理完刪掉）
```

- 預留需求鍵：寫某類時要引用後面才寫的類別的需求（例：UI 要寫「檢核見 RULE-###」，但 RULE 還沒寫），就在這裡登記該類的下一個鍵。寫到該類時，先寫預留鍵的列，再接續編號；寫完就在「被誰引用」後加「已寫」。

## 第 0 章 文件資訊（含目次）（輸出檔：README.md）

**這章回答什麼**：讀者第一眼要知道的事：這是哪份業務需求文件、版本與狀態、根據哪一版來源 Spec、各章在哪個檔。

**從來源哪裡找**：
- 業務名稱：來源入口檔（README、index、檔名以 00 開頭的檔）的標題；沒有入口檔，就用各檔標題共同出現的業務名稱。
- 來源 Spec 版本照抄 2.4 的「版本或日期」；其餘欄位不從來源找，照下方規則填。

**寫法**：README.md 由上而下寫四段：檔頭、說明、文件資訊、目次。
- 檔頭：`# 〈業務名稱〉業務需求文件`。
- 說明，**固定文字**：
  > 本文件依來源 Spec 整理本期的業務需求，只談業務需求，不談系統設計。每條需求都有需求鍵與來源位置；全部需求見第 4 章需求索引，未解的問題見第 7 章。
- 文件資訊：標題 `## 文件資訊`，表頭 `| 項目 | 內容 |`，固定六列，順序與填法如下。

| 項目 | 內容怎麼填 |
|---|---|
| 版本 | 初寫填 `0.1`；之後由人更新 |
| 擁有者 | 初寫一律填 `〈待填〉` |
| 讀者 | 固定填「業務窗口、業務驗收人員、依本文件實作的團隊」 |
| 狀態 | 初寫一律填「草稿」；之後由人更新 |
| 根據的來源 Spec 版本 | 照抄 2.4「版本或日期」；2.4 是〈待填〉就填〈待填〉 |
| 產出日期 | 寫 README 當天的日期，格式 `YYYY-MM-DD`；不知道今天日期就填〈待填〉 |

- 目次：標題 `## 目次`，表頭 `| 章 | 標題 | 檔案 |`，固定下列 18 列，檔案欄寫成連結 `[<檔名>](<檔名>)`。

## 第 1 章 目標（輸出檔：01-goals.md）

**這章回答什麼**：業務窗口看：本期要支援哪些業務、怎樣算成功、哪些事不是本期目標。

**從來源哪裡找**：不重讀來源。1.1、1.3 從自己寫好的 `03-reading-guide.md` 3.3 的 SCOPE 需求整理；1.2 是固定文字。

**寫法**：檔頭 `# 1 目標`，各節標題 `## 1.1 本期要支援哪些業務`、`## 1.2 成功指標`、`## 1.3 不是目標`。
- **1.1 本期要支援哪些業務**（由來源整理）：先寫**固定文字**，再寫表。
  > 本期支援下列業務。完整範圍（包含、依賴、排除）見第 3 章 3.3。
  - 表頭：`| 業務 | 說明 | 需求鍵 |`。
  - 只列 3.3 範圍類型為「包含」的 SCOPE 需求；依賴、排除不列在這裡。
  - 來源的範圍章節把項目分組（例：依業務或作業分組）時，一組一列，需求鍵欄列該組全部 SCOPE 需求鍵，用頓號分開。來源沒有分組時，一條 SCOPE 需求一列。
  - 業務欄用來源的功能名稱；說明欄一句話，從該 SCOPE 需求的描述縮寫，不加新內容。
  - 每條「包含」的 SCOPE 需求在本表恰好出現一次。順序照 3.3。
- **1.2 成功指標**（固定文字，整段照抄）：
  > 本期在下列四項都成立時算成功：
  > 1. 業務情境都能走完：第 9 章 9.1 的每個驗收情境，業務人員都能照步驟操作到結束。
  > 2. 每個需求都已確認或已登記為假設：第 4 章需求索引的每一條需求（確認狀態為「排除」者除外），確認狀態是「已確認」，或「相關假設」欄指向一筆假設。
  > 3. 假設全部收斂：第 7 章 7.2 每筆假設的狀態都是「已關閉」。
  > 4. 業務驗收通過：第 9 章 9.1 的每個驗收情境，在 9.2 都有「通過」的最新紀錄。
  - 不增減項目。來源寫的業務成效目標不寫在這裡（是否列為 OTHER 需求由 5.8 判斷）。
- **1.3 不是目標**：先寫**固定文字**，再寫來源排除的項目。
  > 本期不追求下列事項：
  > - 不追求與舊系統完全等價：舊系統有、來源 Spec 沒寫的行為，本期不做。
  > - 不做來源 Spec 沒寫的業務：來源沒寫的業務行為不寫成需求，改登記假設（見第 7 章）。
  > - 不談系統設計：資料怎麼存、系統怎麼做、怎麼與其他系統串接，不在本文件。
  - 接著寫表，表頭 `| 排除項目 | 需求鍵 |`，列 3.3 範圍類型為「排除」的每條 SCOPE 需求，順序照 3.3。
  - 3.3 沒有「排除」時，不寫表，改寫一行「來源未列排除項目。」

**找不到或有問題時**：
- 3.3 沒有任何「包含」：1.1 表只寫一列 `| 來源未涵蓋 | — | — |`。缺口的假設在 3.3 登記，本章不另登記。
- 本章只引用 3.3，不新增需求、不新增假設、不改 3.3。

**不要寫**：專案時程、預算、人力；效能、可用性、技術或架構目標；舊系統問題分析或改善建議；1.2 以外自訂的成功指標。

**範例**：
```markdown
## 1.1 本期要支援哪些業務
| 業務 | 說明 | 需求鍵 |
|---|---|---|
| 借用申請 | 申請人填借用單並送審 | SCOPE-001 |
| 審核 | 主管核准或退回借用單 | SCOPE-002 |
| 點交與歸還 | 設備管理員登記借出與歸還 | SCOPE-003、SCOPE-004 |
```

## 第 2 章 Spec 是什麼（輸出檔：02-spec-overview.md）

**這章回答什麼**：讀者看：來源 Spec 由哪些檔組成、每份回答什麼業務問題、本文件怎麼用它、來源的狀態標記怎麼對到確認狀態、根據哪一版。

**從來源哪裡找**：
- 列出 `<來源資料夾>` 下的全部檔（含子資料夾、圖檔、試算表）。每檔只讀標題與開頭約 30 行，不精讀。
- 狀態標記：用關鍵字搜尋全部來源，不精讀。關鍵字至少包含：草稿、待確認、已確認、確認、未定、待補、TBD、TODO、缺證據、推定、排除、不做、本期不含、`?`。也找來源自己的圖例或標記說明段落。
- 版本：依序找入口檔檔頭的版本欄、修訂紀錄最後一筆、檔名中的版本或日期；用第一個找到的。

**寫法**：檔頭 `# 2 Spec 是什麼`，各節標題照 2.1～2.4。
- **2.1 唯一業務真相**（固定文字，整段照抄）：
  > 來源 Spec 是本期唯一的業務真相。本文件每條需求都要能指回來源 Spec 的位置。
  > 來源 Spec 沒寫的業務行為，本文件不補，也不用舊系統（例如 PeopleSoft）或業界的一般做法推定。
  > 來源 Spec 有缺漏、矛盾、未完成或看不懂之處，一律登記為假設（見第 7 章），交業務窗口或 Spec 產製端確認。
> 假設依業務窗口的回覆或 Spec 產製端補查後的新版關閉（見第 7 章 7.4）；業務窗口的回覆視為來源 Spec 的補充。
  > 本文件不修改來源 Spec。
- **2.2 組成與每份回答什麼業務問題**：表頭 `| 檔名 | 回答什麼業務問題 | 本文件怎麼用 |`。
  - 一個檔一列；子資料夾的檔寫相對路徑。來源是單一檔時，一個第一層章節一列，檔名欄寫 `<檔名> §<章節>`。入口檔排第一，其餘照檔名排序。
  - 回答什麼業務問題：寫成一個業務問句，以「？」結尾，不超過 40 字，例「借用單有哪些欄位、哪些必填？」。「本文件怎麼用」是 `只取業務意義` 或 `本文件不使用：屬系統設計` 的檔，寫「（系統設計）〈主題〉」。修訂紀錄、撰寫格式檢查表這類輔助檔寫「（輔助）〈用途〉，用於 〈節號〉」。
  - 本文件怎麼用：只填下列三個值之一。
    - `使用`：內容是範圍、流程、畫面、業務資料、規則、狀態、權限、外部往來、驗收、問題清單，或是輔助檔。
    - `只取業務意義`：主體是資料表、欄位型別、程式、API、架構，但夾有可確認的業務意義（例：某資料要保留每次異動的歷史、某代碼值的意思）。
    - `本文件不使用：屬系統設計`：整份都是系統設計，找不到業務意義（例：實作工作項、部署、效能、測試自動化）。
    - 拿不準是後兩者哪一個時，填 `只取業務意義`。
    - 一份檔同時有驗收情境與測試環境、效能、自動化這類內容 → 填 `使用`，只用驗收情境那幾節。
    - 入口檔（索引、README）填 `使用`，「回答什麼業務問題」寫「（輔助）文件組成與狀態標記，用於 2.3、2.4」。
- **2.3 狀態標記**：表頭 `| 來源標記（原文） | 出現位置 | 意思 | 對應確認狀態 |`。
  - 一種標記一列。標記原文照抄，用「」框起。出現位置寫第一次出現處 `<檔名> §<章節>`。
  - 意思：來源有圖例或說明就照它寫；沒有就寫「來源未定義」。
  - 對應確認狀態只填 `已確認`／`待確認`／`排除`：表示已確認、已核定 → `已確認`；表示草稿、待確認、未定、待補、缺證據、推定 → `待確認`；表示本期不做、排除 → `排除`；意思是「來源未定義」→ `待確認`。
  - 問題清單的題目狀態（開放、已回覆）、檢查表的通過／未通過，不是內容的狀態標記，不列。
  - 表末固定加一列：`| （無標記） | — | 來源沒有標狀態 | 內容清楚 → 已確認；不清楚 → 待確認 |`。表裡只有這一列時，表下寫一行「來源未使用狀態標記。」
  - 寫後面各章時遇到表裡沒有的標記：先在本表末（無標記列之前）追加一列，再照它判斷。
- **2.4 版本與取得**：表頭 `| 項目 | 內容 |`，固定五列，順序與填法：
  - 版本或日期：照抄來源原文（例「v1.2」「2026-05-01」）；找不到填〈待填〉；各檔不同填「各檔不同」，並在表下加表 `| 檔名 | 版本或日期 |`，每檔一列。
  - 版本出處：`<檔名> §<章節>`；找不到填「—」。
  - 取得位置：交付給你的 `<來源資料夾>` 路徑，照抄。
  - 使用方式：固定填「唯讀；本文件不修改來源 Spec」。
  - 改版時：固定填「依第 8 章處理」。

**找不到或有問題時**：本章不登記假設。版本找不到填〈待填〉；標記意思不明填「來源未定義」並對到 `待確認`，假設在用到這個標記的需求所在章登記。

**不要寫**：各檔內容摘要或需求；系統設計檔的內容；對來源品質的評語；修改來源檔名或原文。

**範例**：
```markdown
## 2.2 組成與每份回答什麼業務問題
| 檔名 | 回答什麼業務問題 | 本文件怎麼用 |
|---|---|---|
| 03-fields.md | 借用單有哪些欄位、哪些必填？ | 使用 |
| 07-data-model.md | （系統設計）資料表結構 | 只取業務意義 |
| 12-tasks.md | （系統設計）實作工作項 | 本文件不使用：屬系統設計 |

## 2.3 狀態標記
| 來源標記（原文） | 出現位置 | 意思 | 對應確認狀態 |
|---|---|---|---|
| 「〔草稿〕」 | 05-rules.md §2 | 來源未定義 | 待確認 |
| （無標記） | — | 來源沒有標狀態 | 內容清楚 → 已確認；不清楚 → 待確認 |
```

## 第 3 章 怎麼讀 Spec（輸出檔：03-reading-guide.md）

**這章回答什麼**：讀者（含寫後續各章的你自己）看：照什麼順序讀來源、每類內容在哪、來源的排版與表格怎麼解讀、本期範圍是什麼（SCOPE 需求在此編號）、哪些地方容易讀錯。

**從來源哪裡找**：
- 3.1、3.2：從 2.2 的表與各檔標題找，只讀到能判斷內容類別的程度；3.4 從寫 3.1～3.3 時讀到的段落找。
- 3.3：找標題或內文含「範圍」「Scope」「本期」「包含」「不包含」「排除」「依賴」「前提」「out of scope」的章節，以及功能清單、畫面清單、物件清單。

**寫法**：檔頭 `# 3 怎麼讀 Spec`，各節標題照 3.1～3.4。
- **3.1 閱讀順序**：先寫**固定文字**，再寫表。
  > 照下表順序讀來源 Spec；前面的內容是讀懂後面內容的前提。
  - 表頭 `| 順序 | 內容 | 來源位置 | 整理到 |`，固定九列。順序、內容、整理到三欄照抄：1 範圍 3.3／2 業務資料 5.3／3 畫面 5.2／4 規則 5.4／5 狀態 5.5／6 流程 5.1／7 權限 5.6／8 外部往來 5.7／9 驗收 9.1。
  - 來源位置：寫 `<檔名> §<章節>`，多處用頓號分開；只列 2.2 中「使用」或「只取業務意義」的檔。來源沒有這類內容，寫「來源未涵蓋」。
- **3.2 Spec 地圖**：先寫**固定文字**，再寫兩張表。
  > 各類內容的位置見 3.1。本節說明來源的排版慣例與表格欄位意義，後續各章照這裡的解讀讀來源。
  - 兩張表的「意思」照來源的圖例或說明寫；來源沒說明、但欄名或樣式本身意思清楚（例「標籤」「必填」「預設值」）→ 用一句話寫出意思；只有符號、縮寫、代碼沒有圖例才寫「來源未定義」。
  - 「影響判讀」＝會改變某條需求某一欄的值（例：必填、可改條件、出現條件、允許）。
  - 排版慣例：表頭 `| 慣例（原文或樣式） | 出現位置 | 意思 |`。只列會影響需求判讀的慣例：符號或樣式（例「*」「※」、粗體、刪除線）、空白格與「—」「N/A」「同上」、代碼與顯示文字並列的寫法、範例或示意段落的標示。標題編號這類不影響判讀的不列。沒有就寫一行「未發現影響判讀的排版慣例。」
  - 表格欄位意義：表頭 `| 表格位置 | 欄位（原文） | 意思 | 整理到 |`。列出整理需求會用到的每種表格的每個欄位；相同表頭出現在多處只列一次，表格位置用頓號列出各處。整理到填本文件的類別或欄位（例「UI 必填」「來源欄」），型別、長度、技術名稱這類欄位填「不使用：屬系統設計」（只寫這幾個字，不重述欄名）。
- **3.3 範圍判讀**：SCOPE 需求在這裡編號並寫完整內容。
  - 表頭 `| 需求鍵 | 範圍類型 | 項目 | 描述 | 來源 | 確認狀態 | 相關假設 |`。
  - 範圍類型只填三個值：`包含`（本期要支援）、`依賴`（本期要用、但不由本期建立或維護，例：其他系統提供的資料；來源寫「不在本功能範圍」但本功能要用的前提也列依賴，例：角色指派由現有的權限管理功能處理）、`排除`（來源明說本期不做）。
  - 項目：功能、畫面、報表、作業或業務物件的業務名稱，一個一條。欄位只在來源明說「排除」或「依賴」時才單列，一個欄位一條，項目寫 `〈物件〉：〈欄位〉`；「包含」的欄位不在 3.3 列，在第 5 章寫。
  - 描述：一句業務語言。排除的寫出來源給的原因，例「來源註明本期不做」。
  - 確認狀態：範圍類型為「排除」的填 `排除`；其餘照 2.3 判斷，相關假設指向開放的假設時一律填 `待確認`。
  - 排列與編號：先「包含」、再「依賴」、再「排除」，各組內照來源出現順序；需求鍵照這個順序從 SCOPE-001 依序給號。
  - 來源有區分核心與非核心（例：必要／選用、第一階段／後續）時，在描述開頭寫來源原文用語，例「（來源：選用）」。來源沒有區分時，表下寫**固定文字**：
    > 來源 Spec 未區分核心與非核心，範圍內一律視為核心。
- **3.4 常見誤讀**：表頭 `| 位置 | 容易誤讀成 | 正確讀法 | 依據 |`。
  - 只寫這份來源實際出現的誤讀風險。每條都要有位置 `<檔名> §<章節>`，依據寫支持正確讀法的來源位置。
  - 要檢查的情形：同一個詞在不同檔意思不同；範例資料或示意畫面看起來像需求；舊系統現況描述看起來像本期要做；系統設計段落裡夾著業務意義；代碼值與顯示文字不同；空白格可能是「不適用」也可能是「未填」。
  - 正確讀法無法從來源確定的，不列在 3.4，改登記假設（類型「看不懂」）。
  - 一條都沒有時，只寫一行「未發現」。

**找不到或有問題時**：
- 來源沒有任何範圍章節：以來源描述到的每個功能或畫面各寫一條「包含」，並登記假設（類型「缺漏」；缺什麼「本期範圍未明列」；暫定做法「以來源描述到的功能為範圍，未描述的不做」；該問誰「業務窗口」），每條 SCOPE 需求的相關假設填這筆。

- 3.2 的「來源未定義」會影響某條需求的判讀時，登記假設（類型「看不懂」）。
- 3.1 的「來源未涵蓋」不在本章登記假設；缺口在第 5 章各類登記。
- 本檔超過 150 行時，從 3.3 表中間依列拆到 `03-reading-guide-02.md`，續檔重寫表頭。

**不要寫**：來源內容的抄錄或摘要；SCOPE 以外類別的需求；「包含」的欄位清單；技術名稱（只能出現在來源欄）；「要仔細讀」這類一般提醒。

## 第 4 章 從 Spec 整理業務需求（輸出檔：04-requirement-index.md）

**這章回答什麼**：讀者用一張表查全文件有哪些需求、在哪一章、確認到哪裡；也說明什麼算一條需求、怎麼分類、來源的 checklist 怎麼用。

**從來源哪裡找**：
- 4.1、4.2 是固定文字；4.3 也不讀來源，從自己寫好的 3.3（`03-reading-guide.md`）、5.1～5.8（`05-*.md`）、9.1（`09-acceptance.md`）彙整。
- 4.4：找檔名或標題含 checklist、檢查表、檢核表、驗收清單、自我檢查的段落，以及由勾選框（`- [ ]`、`□`）組成的條列或表。

**寫法**：檔頭 `# 4 從 Spec 整理業務需求`，各節標題照 4.1～4.4。
- **4.1 需求單元與需求鍵**（固定文字，整段照抄）：
  > 一條需求是一條可被業務人員獨立確認對錯的業務陳述。
  > 一句話裡有兩件可以分別對錯的事，拆成兩條；條件與它的結果、訊息是同一件事，不拆。
  > 同一件事在來源多處出現，寫成一條需求，來源欄列出各處；各處寫法矛盾時仍寫一條，並登記假設。
  > 需求鍵格式為 `<類別碼>-<三位序號>`，例 `RULE-007`，只用 ASCII。序號在各類別內從 001 起依序給號；已跳號就照實保留，不補號、不改號。
  > 需求鍵在完整內容所在章給號：SCOPE 在 3.3，ACC 在 9.1，OTHER 在 5.8，其餘在 5.1～5.7；需求索引不另給號。
  > 來源 Spec 自己的編號寫在「來源」欄，不當需求鍵。
  > 需求鍵一經發布不改、不重用。刪除的需求保留列，確認狀態改「排除」，並註明原因。
  - 拆與不拆的判斷例（給你判斷用，不寫進產出）：
    - 拆：「借用期間不得超過 14 天，且開始日不得早於今天」→ 兩條 RULE。
    - 拆：「主管可核准或退回」→ 核准、退回各一條 STATE。
    - 不拆：「借用期間超過 14 天時顯示『借用期間不得超過 14 天』，不能送審」→ 一條 RULE。
    - 不拆：一個代碼與它的全部選項值 → 一條 DATA。
- **4.2 需求分類**：先照抄類別表（固定），表頭 `| 類別碼 | 類別 | 寫什麼 | 完整內容寫在 |`，類別碼、類別、寫什麼三欄照通用規則的類別碼表，「完整內容寫在」欄：SCOPE 填 3.3，FLOW～EXT 填 5.1～5.7 對應檔，ACC 填 9.1，OTHER 填 5.8。表下寫**固定文字**：
  > 一條需求只歸一類。各類的細部界線以第 5 章為準；第 5 章沒說明時，照下列順序，第一個符合的就是它的類別：
  > 1. 講本期做不做 → SCOPE；2. 講驗收時怎麼操作驗證 → ACC；3. 講兩個以上步驟的先後 → FLOW；
  > 4. 講狀態的進入、離開、誰能觸發 → STATE；5. 講誰能看、能改、能看到哪些範圍的資料 → PERM；
  > 6. 講與其他系統交換什麼 → EXT；7. 講條件成立時的結果或訊息 → RULE；8. 講畫面上看到、能操作什麼 → UI；
  > 9. 講資料的意義、代碼值、是否保留歷史 → DATA；10. 以上都不是 → OTHER。
- **4.3 需求索引**：
  - 標題下第一行寫數量（固定格式）：`共 〈N〉 條：SCOPE 〈n〉、FLOW 〈n〉、UI 〈n〉、DATA 〈n〉、RULE 〈n〉、STATE 〈n〉、PERM 〈n〉、EXT 〈n〉、ACC 〈n〉、OTHER 〈n〉。`（含確認狀態為「排除」者）
  - 表頭（固定，不增減欄）：`| 需求鍵 | 類別 | 摘要 | 來源 | 確認狀態 | 相關假設 |`。
  - 類別：填 4.2 的「類別」欄中文名稱，例「業務規則」。
  - 摘要：一句，不超過 40 字，從完整內容縮寫，不加新內容，不含技術名稱與「|」。
  - 來源、確認狀態、相關假設：照抄完整內容那一列。照抄時發現確認狀態是「已確認」、但相關假設指向開放的假設：兩處都改成「待確認」。
  - 排序：先依類別碼順序 SCOPE → FLOW → UI → DATA → RULE → STATE → PERM → EXT → ACC → OTHER，同類別內依序號。
  - 3.3、5.1～5.8、9.1 的每個需求鍵在本表恰好出現一次；本表不新增、不刪除需求。序號有跳號時照實列，不補號。
  - 拆檔：每個檔不超過 150 行。超過時在表格列與列之間拆到 `04-requirement-index-02.md`、`-03.md`；續檔檔頭 `# 4 從 Spec 整理業務需求（續 02）`、節標題 `## 4.3 需求索引（續）`，重寫表頭；主檔末尾列出各續檔。
- **4.4 checklist 怎麼用**：
  - 先判斷來源有沒有 checklist（找法見上）。沒有：只寫**固定文字**
    > 來源無 checklist。
  - 有：逐份判斷種類，一份裡兩種都有時逐項判斷。項目講業務要有的行為或要驗證的情境（例「主管退回後，申請人可修改再送審」）→ 需求或驗收清單；項目講 Spec 文件本身怎麼寫（例「每個欄位都有說明」）→ 撰寫品質或格式檢查表。
  - 需求或驗收清單：每一項都要對到需求鍵。表頭 `| checklist 項目（原文） | 來源 | 對應需求鍵 | 說明 |`；項目原文照抄，用「」框起；一項可對多個需求鍵，用頓號分開；說明寫「—」或對應方式。對不到的項目：內容是業務行為，就在該類完整內容檔末尾補一條需求（給下一個序號）；是驗收情境，就在 9.1 末尾補一條 ACC；同時補進 4.3，說明欄寫「4.4 補列」。
  - 撰寫品質或格式檢查表：不逐項對照，不轉成需求，只拿來檢查 4.3 有沒有漏。寫**固定文字**一句：
    > 來源 checklist〈檔名 §章節〉屬撰寫品質或格式檢查表，只用於檢查需求索引有無遺漏；結果：〈未發現遺漏／發現遺漏，已補列 〈需求鍵〉〉。

**找不到或有問題時**：4.3 不登記新假設；需求的缺口在完整內容所在章登記。checklist 項目講的業務在來源其他地方沒寫、意思不明時，補列的需求確認狀態填 `待確認`，並登記假設（類型「看不懂」）。

**不要寫**：需求的完整描述；第二套編號；系統設計或技術名稱；把撰寫品質檢查項目轉成需求；4.3 自行改寫確認狀態（上述開放假設的情形除外）。

## 第 5 章 各類業務需求的讀法與確認重點（輸出檔：05-1-flows.md … 05-7-interfaces.md、05-8-coverage.md）

### 5 章共通規則（5.1～5.8 都適用）

**這章回答什麼**：業務人員看了這章，能逐條判斷「系統要這樣做，對不對」。一類一個檔；每條需求只在一處寫完整內容（見第 4 章）。

**一條需求怎麼拆**
- 一條需求＝一條業務人員不用看別條就能判斷對錯的陳述。
- 要拆：陳述裡用「或」連接、或列了多個對象、多個結果，而每一半都能單獨判斷對錯。
- 不拆：用「且」連接的條件；拆出來的那一半沒有自己的來源位置、只是重述另一條。
- 各類的拆法寫在各節「寫法」第 1 點；條數以該拆法為準，不另加「總結條」。

**表格與欄位**
- 5.2～5.7 用表格，5.1 用條列區塊。表頭由各節給出，不增減欄、不改欄名、不改欄序。
- 每類都有：需求鍵、描述、來源、確認狀態、相關假設。描述照各節給的句型寫一句。
- 欄位值三種寫法：來源有寫 → 照寫；來源明寫「沒有」「不限」→ 寫 `無`；來源沒提 → 寫 `—`，不作陳述。
  各節標「必答」的欄位，來源沒提時改寫 `來源未涵蓋` 並登假設。
- 畫面標籤、訊息文字、代碼值、狀態名稱照抄原文並用「」框起；其餘用業務語言改寫。
- 欄位一律用畫面標籤或業務名稱稱呼。來源只有技術名時，描述用業務名稱，技術名寫進「來源」欄：`〈檔名〉 §〈節〉（原名 〈技術名〉）`。
- 排序照來源 Spec 出現順序。每檔以 `### 〈群組〉` 分小節，群組方式各節規定。
- 確認狀態照第 6 章 6.2 的判定；相關假設照第 7 章 7.2 的格式。
- 每檔開頭固定文字：
  > 本檔列出〈類別名〉需求 〈N〉 條（待確認 〈M〉 條、排除 〈K〉 條）。來源：〈檔名清單〉。假設見 `07-assumptions.md`。
- 每檔末尾一行：`續檔：〈無／檔名清單〉`。

**歸屬類別（同一件事只寫在一類）**

| 內容 | 寫在 | 其他類只寫引用 |
|---|---|---|
| 欄位的必填、預設、可改／唯讀條件、出現／隱藏條件（條件依狀態或其他欄位值） | UI | — |

| 查詢清單列出哪些資料、怎麼排序 | UI（畫面列描述） | 不立 RULE |
| 選項清單、代碼值與意思 | DATA | UI 描述「選項見 DATA-###」 |

### 5.1 流程與業務情境（輸出檔：05-1-flows.md，類別碼 FLOW）

**這章回答什麼**：業務人員看了知道誰在什麼時機做什麼、接著誰做什麼、退回或出錯時怎麼走。

**從來源哪裡找**：標題含「流程」「作業」「情境」「步驟」「使用案例」「Flow」的章節；流程圖、泳道圖的文字說明；「送出後」「核准後」「退回」「取消」「逾期」等字眼；畫面章節裡的「按下〈按鈕〉後」。

**寫法**
1. 拆法：一條路徑一條需求。正常路徑（從觸發到結束）一條；每個例外路徑（退回、取消、逾期、補件）各一條，寫從哪一條的第幾步分出、回到第幾步或在哪結束。觸發者或起點不同 → 各一條。來源寫成一條主要流程的，整條寫成一條正常路徑，不因各步執行者不同而拆。單一步驟不獨立成條。
2. 群組：一個業務情境一個 `### 〈情境名〉` 小節，正常路徑在前、例外路徑在後。
3. 每條用條列區塊，欄名與順序固定：
   ```
   #### FLOW-### 〈路徑名〉
   - 描述：〈角色〉在〈時機〉〈做什麼〉，結果〈結果〉。
   - 路徑類型：正常／例外（分出自 FLOW-### 第 n 步）
   - 觸發：〈誰、什麼時機〉
   - 角色：〈參與的角色，頓號分開〉
   - 步驟：1. 〈角色〉〈動作〉 2. …（步驟造成狀態轉移或外部往來時，步驟末尾加 → STATE-###／→ EXT-###）
   - 結束：〈結束條件或結果〉
   - 來源：〈〉／確認狀態：〈〉／相關假設：〈〉
   ```
4. 步驟只寫動作與結果，不寫檢核條件（→ RULE）、不寫誰有權（→ PERM）。觸發、結束兩欄必答。

**每條都要問**：觸發者是誰？起點與結束條件是什麼？每一步的執行者是誰？退回後回到哪一步、能重送幾次？取消與逾期的路徑有沒有寫？同一步驟能不能重複做？

**找不到或有問題時**：來源只有流程圖沒有文字 → 照圖寫步驟，來源欄註「依圖」，確認狀態 `待確認`，同一張圖合併登一筆假設（類型 看不懂）。其他類有提到（狀態、動作、訊息）但流程沒寫的例外路徑 → 不寫該條，在正常路徑的「相關假設」登一筆（類型 缺漏，暫定做法「不提供該路徑」）；來源完全沒提的例外不寫、不登。

**不要寫**：畫面欄位（→ UI）、檢核與訊息（→ RULE）、狀態定義（→ STATE）、權限（→ PERM）、通知或取資料的內容（→ EXT）、批次排程與程式的實作。

**範例**
```

- 描述：申請人填借用單送審，主管核准後由設備管理員點交，歸還時結案。
- 路徑類型：正常
- 觸發：申請人需要借用設備時
- 角色：申請人、主管、設備管理員
- 步驟：1. 申請人填借用單並送出 → STATE-003、→ EXT-001 2. 主管核准 → STATE-004、→ EXT-002 3. 設備管理員點交 → STATE-005 4. 申請人歸還，設備管理員登記 → STATE-006
- 結束：借用單為「已歸還」

- 描述：主管退回後，申請人修改借用單重新送出，回到 FLOW-001 第 2 步。
- 路徑類型：例外（分出自 FLOW-001 第 2 步）
- 來源：flow.md §2.2／確認狀態：待確認／相關假設：A-003
```

### 5.2 畫面與欄位（輸出檔：05-2-screens.md，類別碼 UI）

**這章回答什麼**：使用者在每個畫面看到什麼、能填什麼、哪些必填、哪些帶預設、什麼時候能改、什麼時候出現。

**從來源哪裡找**：標題含「畫面」「頁面」「欄位」「表單」「清單」「查詢」「UI」「Page」的章節；欄位清單表格（標籤、必填、預設、唯讀等欄）；畫面截圖的文字說明；「顯示」「隱藏」「灰掉」「不可修改」「帶入」等字眼。

**寫法**
1. 拆法：一個畫面一列（類型 `畫面`）＋每個欄位一列（類型 `欄位`）＋每個按鈕或動作一列（類型 `動作`）。一個欄位的必填、預設、可改條件、出現條件寫在同一列，不拆成多條。同一欄位出現在兩個畫面 → 各畫面一列。查詢清單的顯示欄位也是欄位列，可改條件寫 `唯讀`。來源以文字描述清單（沒有欄位表）→ 清單本身一列（類型 `欄位`，標籤寫來源的稱呼，不加「」），顯示的項目寫在描述，不逐項成列。
2. 群組：一個畫面一個 `### 〈畫面名〉` 小節、一張表，畫面列在第一列。
3. 表頭：`| 需求鍵 | 畫面 | 類型 | 欄位標籤 | 描述 | 必填 | 預設 | 可改條件 | 出現條件 | 來源 | 確認狀態 | 相關假設 |`
4. 描述句型：畫面列「〈角色〉用來〈做什麼〉」；欄位列「〈欄位的業務意思〉」；動作列「按下後〈結果〉（→ FLOW-###／STATE-###）」。檢核寫「檢核見 RULE-###」、選項寫「選項見 DATA-###」，接在描述末尾。
5. 值域：必填 `必填`／`選填`／`〈條件〉時必填`／`來源未涵蓋`（可改條件不是 `唯讀` 的欄位列必答）／`—`（可改條件為 `唯讀` 的欄位、查詢清單的顯示欄位、系統帶入且不可改的欄位）；預設 原文「」／`無`／`見 RULE-###`／`—`；可改條件 `一律可改`／`唯讀`／`〈狀態或欄位條件〉時可改`／`—`；出現條件 `一律出現`／`〈條件〉時出現`／`—`。畫面列與動作列的必填、預設寫 `—`。
6. 條件依角色而異 → 可改條件、出現條件寫 `—`，描述寫「權限見 PERM-###」。

**每條都要問**：欄位標籤原文是什麼？必填嗎、什麼條件下必填？有預設值嗎、值從哪來？什麼狀態下能改？什麼條件下才出現？選項從哪來？按下動作後發生什麼？

**找不到或有問題時**：可改的欄位，來源沒提必填（含來源必填欄寫「—」或空白）→ 寫 `來源未涵蓋`，同一畫面合併登一筆假設（類型 缺漏，暫定做法「必填」）；來源必填欄寫「待確認」→ 寫 `來源未涵蓋`，登假設（類型 未完成）。唯讀、顯示用、系統帶入且不可改的欄位，必填寫 `—`，不登假設。來源只有截圖沒有欄位清單 → 照截圖上的標籤列欄位，來源欄註「依截圖」，確認狀態 `待確認`，同一畫面合併登一筆假設（類型 看不懂）。欄位只有技術名 → 描述用業務名稱、來源欄註原名、登假設（類型 看不懂）。

**不要寫**：版面位置、顏色、字型、元件型式（下拉、日曆）、欄位型別與長度；檢核條件的內容（→ RULE）；選項值清單（→ DATA）；角色差異（→ PERM）。

```

|---|---|---|---|---|---|---|---|---|---|---|---|
```

### 5.3 業務資料（輸出檔：05-3-data.md，類別碼 DATA）

**這章回答什麼**：這個業務有哪些資料主體、一筆代表什麼、代碼值與意思、哪些資料要保留歷史。

**從來源哪裡找**：標題含「資料」「代碼」「選項」「參照」「資料字典」「資料庫」「Table」「欄位定義」的章節；畫面章節裡的「選項：」「下拉」；「生效日」「歷史」「版本」「異動紀錄」等字眼。資料庫章節只拿業務意義（見共通規則）。

**寫法**
1. 拆法：每個資料主體（業務上一筆一筆存在的東西）一列（類型 `主體`）；每組代碼值或選項清單一列（類型 `代碼`），全部代碼值寫在同一列；來源明寫、但畫面上不填的業務資料（例如系統記錄的時間、累計值）每項一列（類型 `資料項`）。畫面上填的一般欄位不在這裡重列（→ UI）。來源寫的異動紀錄（例：原狀態、新狀態、異動人、異動時間）寫成一列資料項，項目列在描述，不逐項成列。
2. 群組：一個資料主體一個 `### 〈主體名〉` 小節，主體列在第一列，其代碼與資料項接在後面；跨主體共用的代碼放 `### 共用代碼`。
3. 表頭：`| 需求鍵 | 資料項目 | 類型 | 描述 | 代碼值與意思 | 保留歷史 | 來源 | 確認狀態 | 相關假設 |`
4. 描述句型：主體列「一筆代表〈什麼〉；以〈業務上怎麼認一筆〉區分」；代碼列「〈哪個畫面的哪個欄位〉的選項」；資料項列「〈意思〉，在〈什麼時機〉產生」。
5. 代碼值與意思：`「值」＝意思；「值」＝意思`。超過 10 個 → 寫 `見下表`，表後接一張 `| 代碼值 | 意思 |`。狀態代碼只寫「值」＝「狀態名稱」，意思與轉移在 STATE。非代碼列寫 `—`。
6. 保留歷史：來源有寫才填 `依生效日期`／`每次異動`／`不保留`；沒寫填 `—`，不登假設。

**每條都要問**：業務上怎麼認一筆（同一人借同一設備兩次算一筆還是兩筆）？代碼值完整嗎，有沒有「其他」「停用」？代碼的意思是來源寫的還是只有值？要不要留歷史、留到什麼程度？

**找不到或有問題時**：代碼值只有值沒有意思 → 意思寫 `來源未涵蓋`，登假設（類型 缺漏）。保留歷史沒提 → 寫 `—`，不登假設。來源只有表結構 → 主體與代碼照業務名稱列，來源欄註原名，確認狀態 `待確認`，同一主體合併登一筆假設（類型 看不懂）。

**不要寫**：表名、欄位技術名、型別、長度、主鍵、索引、關聯圖、儲存方式、資料量、效能；誰能維護資料（→ PERM）。

**範例**
```

| 需求鍵 | 資料項目 | 類型 | 描述 | 代碼值與意思 | 保留歷史 | 來源 | 確認狀態 | 相關假設 |
|---|---|---|---|---|---|---|---|---|
| DATA-001 | 借用單 | 主體 | 一筆代表一次借用申請；同一申請人同一設備不同期間算不同筆 | — | 每次異動 | data.md §1（原名 LOAN_REQ） | 已確認 | — |
```

### 5.4 業務規則（輸出檔：05-4-rules.md，類別碼 RULE）

**這章回答什麼**：什麼條件下系統要擋下、警告、自動帶值或計算；顯示什麼訊息。

**從來源哪裡找**：標題含「規則」「檢核」「驗證」「邏輯」「計算」「訊息」「Rule」「Validation」的章節；「若」「當」「不得」「必須」「超過」「不可」「自動」等字眼；訊息清單表；畫面欄位表的「檢核」「備註」欄；程式說明章節只拿可確認的業務條件與結果。

**寫法**
1. 拆法：一個條件→一個結果一條。同一條件、多個結果 → 每個結果一條，條件重寫。條件以「或」連接 → 每個分支一條；以「且」連接 → 一條。同一規則在多個時機檢核 → 每個時機一條。
2. 群組：依規則所屬的畫面或流程一個 `### 〈畫面或流程名〉` 小節；多處共用的放 `### 共用`。
3. 表頭：`| 需求鍵 | 描述 | 時機 | 條件 | 結果 | 結果類型 | 訊息原文 | 來源 | 確認狀態 | 相關假設 |`
4. 描述句型：「〈時機〉，若〈條件〉，則〈結果〉」。
5. 值域：時機 `輸入時`／`送出時`／`〈動作〉時`／`〈事件〉時`（例「借用起日前 1 日時」）／`每日`／`來源未涵蓋`（必答）；結果類型 `阻擋`／`警告`／`自動帶值`／`計算`／`其他`；訊息原文 照抄「」／`無`（來源明寫無訊息）／`來源未涵蓋`（結果類型為阻擋、警告時必答）／`—`（結果類型不是阻擋、警告，且來源沒提訊息）。
6. 條件含數值或日期比較時，條件欄要寫到邊界：「超過 30 天（第 31 天起）」「早於今天（今天可送）」。來源沒寫邊界 → 照原文寫，登假設（類型 看不懂）。

**每條都要問**：什麼時候檢核？邊界值算不算？結果是擋下還是只提醒？訊息原文是什麼？條件裡的每個值（天數、金額、角色）來源有沒有寫？擋下後使用者能做什麼？

**找不到或有問題時**：訊息原文沒寫 → `來源未涵蓋`，同一來源檔合併登一筆（暫定做法照 7.2 暫定做法表）。來源把訊息列在錯誤訊息表，或訊息含「無法」「不得」「不可」→ 結果類型 `阻擋`，不登假設；只有來源寫「提示」「提醒」又沒說能否繼續，才寫 `阻擋` 並登假設。來源有訊息沒有條件 → 仍一條，條件 `來源未涵蓋`，確認狀態 `待確認`，登假設（類型 缺漏）。

**不要寫**：程式邏輯、SQL、演算法步驟；單純格式與長度檢核（屬系統設計）；欄位的必填、預設、出現條件（→ UI，必填不是 RULE）；狀態轉移本身（→ STATE）；誰有權（→ PERM）。

**範例**
```
### 借用單
| 需求鍵 | 描述 | 時機 | 條件 | 結果 | 結果類型 | 訊息原文 | 來源 | 確認狀態 | 相關假設 |
|---|---|---|---|---|---|---|---|---|---|
| RULE-001 | 送出時，若借用期間超過 30 天，則不得送出 | 送出時 | 借用期間結束日－起始日超過 30 天（第 31 天起） | 不得送出 | 阻擋 | 「借用期間不得超過 30 天」 | rule.md §2 第 1 列 | 已確認 | — |
| RULE-002 | 送出時，若借用起始日早於今天，則不得送出 | 送出時 | 起始日早於今天（今天可送） | 不得送出 | 阻擋 | 來源未涵蓋 | rule.md §2 第 2 列 | 待確認 | A-005 |
| RULE-003 | 每日，若已借出且超過歸還日未歸還，則標示逾期 | 每日 | 狀態「已借出」且今天晚於歸還日（歸還日當天不算） | 借用單標示「逾期」 | 其他 | 無 | rule.md §3 | 已確認 | — |
```

### 5.5 狀態與生命週期（輸出檔：05-5-states.md，類別碼 STATE）

**這章回答什麼**：一筆資料從建立到結束經過哪些狀態、誰在什麼條件下把它推到下一個狀態、哪些轉移不允許。

**從來源哪裡找**：標題含「狀態」「生命週期」「狀態圖」「Status」「Workflow」的章節；狀態轉移表、狀態圖的文字說明；「狀態改為」「變為」「不得退回」「不可取消」等字眼；代碼章節裡的狀態清單（值→ DATA，轉移→ 這裡）。

**寫法**
1. 拆法：每個有狀態的主體：每個狀態一條（狀態表）；每個允許的轉移一條；每個來源明寫禁止的轉移一條（轉移表）。同一轉移由不同觸發者觸發 → 各一條。來源沒寫的轉移組合不列、不推定（見下）。
2. 群組：一個主體一個 `### 〈主體名〉` 小節，先狀態表、再轉移表。
3. 狀態表表頭：`| 需求鍵 | 狀態 | 描述 | 起始／終止 | 來源 | 確認狀態 | 相關假設 |`。起始／終止 值域 `起始`／`終止`／`—`。描述句型：「〈這個狀態下業務上代表什麼、能做什麼〉」。
4. 轉移表表頭：`| 需求鍵 | 從 | 到 | 觸發者 | 條件 | 允許 | 描述 | 來源 | 確認狀態 | 相關假設 |`。允許 值域 `允許`／`禁止`；觸發者 角色名或 `系統`（允許列必答，禁止列 `—`）；條件 `無`／〈條件〉／`見 RULE-###`／`—`。描述句型：允許列「〈觸發者〉〈動作〉後，〈從〉變為〈到〉」；禁止列「〈從〉不得變為〈到〉」。
5. 狀態名稱照原文「」；代碼值不寫這裡（→ DATA）。

**每條都要問**：起始狀態是哪個、終止狀態有幾個？每個轉移誰能觸發？轉移有沒有附帶條件？能不能回到前一個狀態、能回幾次？禁止的轉移來源有沒有明寫？停在某狀態有沒有時限？

**找不到或有問題時**：
- 來源沒寫到的轉移組合 → 不逐一列。每個主體在轉移表末加一列：從「（其他未列出的轉移）」、到 `—`、觸發者 `—`、條件 `—`、允許 `禁止`、描述「未列出的轉移一律不允許」，確認狀態 `待確認`，登一筆假設（類型 缺漏，暫定做法「不允許該轉移」），影響的需求鍵只寫這一列；其他轉移列不受影響。來源已明寫「其他轉移一律不允許」→ 這一列確認狀態 `已確認`，不登假設。
- 來源有列的轉移，但觸發者或條件沒寫（例：只寫「見某檔」而該檔沒有）→ 允許欄照來源寫 `允許`，觸發者或條件寫 `來源未涵蓋`，描述末加「（暫不提供，見 A-###）」，登假設（暫定做法「暫不提供該轉移」）。
- 一個動作一次改多筆（例：設備停用時，所有「送審中」的借用單改為「退回」）→ 每個來源狀態一列，觸發者寫做這個動作的角色，條件寫「〈動作〉時一併改」。
- 來源寫「X 為終止狀態，之後不可再變更」→ 狀態表該列起始／終止填 `終止`，不另寫禁止列；只有來源點名的單一禁止轉移（例「退回的借用單不可直接核准」）才寫禁止列。
- 觸發者沒寫（不屬上面情形）→ `來源未涵蓋`，登假設。只有狀態清單沒有轉移 → 只寫狀態表，轉移表位置寫一行「轉移：來源未涵蓋」並登假設。

**不要寫**：步驟順序與畫面操作（→ FLOW、UI）；狀態代碼值（→ DATA）；轉移時的檢核內容（→ RULE，條件欄引鍵即可）；通知（→ EXT）。

**範例**
```

| 需求鍵 | 狀態 | 描述 | 起始／終止 | 來源 | 確認狀態 | 相關假設 |
```

### 5.6 角色與權限（輸出檔：05-6-permissions.md，類別碼 PERM）

**這章回答什麼**：有哪些角色、每個角色是誰、能看哪些畫面與資料、能改什麼、看得到多大範圍的資料。

**從來源哪裡找**：標題含「角色」「權限」「授權」「使用者」「Role」「Security」的章節；權限矩陣表；畫面或流程章節裡的「只有〈角色〉可以」「〈角色〉看不到」；角色定義（「主管指…」）。

**寫法**
1. 拆法：每個角色一條定義列（對象 `（角色定義）`）；每個角色 × 每個對象（畫面、動作或資料主體）一條。同一角色對同一對象的可看、可改、資料範圍寫同一列。來源用矩陣表 → 只有「可」（✓）的格子成條；「不可」（✗）寫進同一對象「可」那列的描述末「其他角色不可」。例外：某格「不可」與來源別處說法矛盾時，那一格仍單獨成條以掛假設。
2. 群組：一個角色一個 `### 〈角色名〉` 小節，定義列在第一列。
3. 表頭：`| 需求鍵 | 角色 | 對象 | 可看 | 可改 | 資料範圍 | 描述 | 來源 | 確認狀態 | 相關假設 |`
4. 描述句型：定義列「〈角色〉指〈誰〉，以〈怎麼認定〉」；權限列「〈角色〉可〈看／改〉〈對象〉的〈範圍〉」。
5. 值域：可看 `可`／`不可`／`〈條件〉時可`／`—`；可改 `可`／`不可`／`〈欄位或動作清單〉`／`〈狀態〉時可`／`—`（可看與可改至少一欄有值，否則不成條）；資料範圍 `本人`／`所屬單位`／`全部`／〈來源寫法〉／`來源未涵蓋`（對象是資料主體且可看為 `可` 時必答；對象是畫面、動作或欄位時寫 `—`）。定義列三欄寫 `—`。
6. 角色的認定來自其他系統 → 定義列描述寫「認定見 EXT-###」。

**每條都要問**：這個角色怎麼認定（職稱、設定、來自哪裡）？看得到哪些人的資料？能改哪些欄位、在什麼狀態下？能執行哪些動作（核准、點交）？有沒有代理或兼任？看不到的資料是整筆隱藏還是唯讀？

**找不到或有問題時**：資料範圍沒寫 → `來源未涵蓋`，每角色合併登一筆（暫定做法「本人」）。來源只在流程裡提到角色、沒有權限章節 → 照流程步驟列「可改＝該步驟的動作」，可看寫 `—`，確認狀態 `待確認`，每角色合併登一筆假設（類型 缺漏）。角色定義沒寫 → 定義列描述寫 `來源未涵蓋`，登假設（類型 缺漏）。

**不要寫**：帳號、登入方式、權限清單技術名、角色對應的系統設定；畫面欄位本身（→ UI）；流程步驟（→ FLOW）。

**範例**
```
### 主管
| 需求鍵 | 角色 | 對象 | 可看 | 可改 | 資料範圍 | 描述 | 來源 | 確認狀態 | 相關假設 |
|---|---|---|---|---|---|---|---|---|---|
| PERM-004 | 主管 | （角色定義） | — | — | — | 主管指申請人的直屬主管，認定見 EXT-001 | perm.md §1 第 2 列 | 已確認 | — |
| PERM-005 | 主管 | 借用單 | 可 | 「核准」「退回」動作、「審核意見」欄位 | 所屬單位 | 主管可看所屬單位的借用單並核准或退回 | perm.md §2 第 2 列 | 已確認 | — |
| PERM-006 | 主管 | 設備清單 | 可 | 不可 | 來源未涵蓋 | 主管可看設備清單 | perm.md §2 第 3 列 | 待確認 | A-007 |
```

### 5.7 與其他系統的往來（輸出檔：05-7-interfaces.md，類別碼 EXT）

**這章回答什麼**：這個業務要從哪裡取得資料、要把什麼送到哪裡（含通知）、什麼時機、對方沒回應或資料不對時業務上怎麼辦。

**從來源哪裡找**：標題含「介面」「整合」「串接」「通知」「外部」「上下游」「Interface」「API」「排程」的章節；「取得」「同步」「發送」「通知」「匯入」「匯出」等字眼；流程步驟裡提到別的系統或「寄信」。API 章節只拿業務意義（見共通規則）。

**寫法**
1. 拆法：一個對象 × 一個交換內容 × 一個時機一條。同一對象、取得與送出 → 各一條。同一內容在兩個時機交換 → 各一條。通知一種訊息一條。
2. 群組：一個對象一個 `### 〈對象名〉` 小節；通知放 `### 通知`，對象欄寫「〈收件角色〉（通知）」。
3. 表頭：`| 需求鍵 | 對象 | 方向 | 交換內容 | 時機 | 失敗時業務處理 | 描述 | 來源 | 確認狀態 | 相關假設 |`
4. 描述句型：「〈時機〉，〈從／向〉〈對象〉〈取得／送出〉〈內容〉」。
5. 值域：方向 `取得`／`送出`；時機 `〈動作〉時`／`每日`／`即時`／`來源未涵蓋`（必答）；失敗時業務處理 〈來源寫法〉／`來源未涵蓋`（必答）。交換內容用業務名稱列項目、頓號分開。通知的交換內容寫來源列的內容項目；來源另有訊息原文才照抄「」。來源只給項目、沒給原文 → 不算缺口、不登假設、不影響確認狀態。

**每條都要問**：對象是哪個系統或單位（用業務稱呼）？交換哪些業務項目？什麼時機、由什麼動作或事件啟動？取不到或對方拒絕時，流程停、人工補、還是照舊？兩邊資料不一致時以哪邊為準？通知給誰、內容是什麼？

**找不到或有問題時**：失敗時業務處理沒寫 → `來源未涵蓋`，每對象合併登一筆（暫定做法「流程停在原狀態，由人工確認」）。來源只有端點或欄位對照表 → 交換內容用業務名稱列，來源欄註原名，確認狀態 `待確認`，同一對象合併登一筆假設（類型 看不懂）。對象只有系統代號 → 對象寫代號原文「」，登假設（類型 看不懂）。

**不要寫**：端點、協定、檔案與訊息格式、欄位對照、重試次數、逾時秒數、認證方式；畫面（→ UI）；角色認定本身（→ PERM，PERM 引鍵即可）。

**範例**
```
### 人事資料
| 需求鍵 | 對象 | 方向 | 交換內容 | 時機 | 失敗時業務處理 | 描述 | 來源 | 確認狀態 | 相關假設 |
|---|---|---|---|---|---|---|---|---|---|
| EXT-001 | 人事資料 | 取得 | 申請人的直屬主管 | 申請人送出借用單時 | 取不到主管時不得送出，由申請人聯絡人事單位 | 送出時，從人事資料取得申請人的直屬主管 | ext.md §1 | 已確認 | — |
### 通知
| 需求鍵 | 對象 | 方向 | 交換內容 | 時機 | 失敗時業務處理 | 描述 | 來源 | 確認狀態 | 相關假設 |
|---|---|---|---|---|---|---|---|---|---|
| EXT-002 | 申請人（通知） | 送出 | 核准通知：「您的借用申請已核准」 | 主管核准時 | 來源未涵蓋 | 核准時，向申請人送出核准通知 | ext.md §2 第 1 列 | 待確認 | A-008 |
```

### 5.8 每一類寫到哪裡、還缺什麼（輸出檔：05-8-coverage.md，含 OTHER）

**這章回答什麼**：業務窗口看一張表就知道每一類需求有幾條、來源寫得夠不夠、還缺什麼；並收納不屬於前面各類的業務需求。

**從來源哪裡找**：不另讀來源。從已寫好的 `03-reading-guide.md`（SCOPE）、`05-1`～`05-7` 各檔與續檔、`09-acceptance.md`（ACC）、`07-assumptions.md` 彙整。OTHER 來自 `progress.md`「待歸類」清單。

**寫法**
1. 涵蓋表（固定 10 列，順序照類別碼表）：`| 類別 | 需求數 | 來源涵蓋情況 | 還缺什麼 | 相關假設 |`
   - 需求數：該類已編號的條數（含 `排除`）。
   - 來源涵蓋情況 值域：`完整`（每條都是 `已確認` 或 `排除`，且無開放假設）／`部分`（有需求，但有 `待確認` 或開放假設）／`來源明示無`（來源明寫無此類）／`來源未涵蓋`（0 條且來源沒提）。OTHER 列 0 條時寫 `—`，不登假設。
   - 還缺什麼：只寫三種——該類開放假設的「缺什麼」摘要、來源自己標的待補項、其他類引用了這類卻沒有對應列的鍵。每項一句、頓號分開；`完整`、`來源明示無` 寫 `—`。不寫猜測、不寫解法。
   - 相關假設：該類全部開放假設的編號。
2. 表後一行固定文字：「引用檢查：〈全部指到既有需求鍵／以下引用無對應列：〈鍵清單〉〉」。有無對應者 → 寫進該類「還缺什麼」並登假設（類型 缺漏）。
3. `## 其他（OTHER）`：表頭 `| 需求鍵 | 描述 | 不屬其他類的原因 | 來源 | 確認狀態 | 相關假設 |`。進入條件：是業務需求、不是系統設計、9 類都放不下。先試歸類，放得下就不進 OTHER。第 7 章 7.1 找不到需求可掛的缺口，也在這裡開一條 OTHER（寫法見 7.1）。沒有 → 表格位置寫一行「無」。
4. 檔末「續檔」照共通規則。

**找不到或有問題時**：某類 0 條 → 照值域填 `來源明示無` 或 `來源未涵蓋`；填 `來源未涵蓋` 的類別要有一筆假設（共通規則已登），編號填入相關假設欄。

**不要寫**：重複各類需求內容；缺口的解法建議；系統設計待辦；對來源品質的評語。

**範例**
```
| 類別 | 需求數 | 來源涵蓋情況 | 還缺什麼 | 相關假設 |
|---|---|---|---|---|

| FLOW | 4 | 部分 | 退回後重送次數上限 | A-003 |

（範例省略 DATA、RULE、PERM、ACC 四列）
引用檢查：全部指到既有需求鍵
```

## 第 6 章 需求追蹤（輸出檔：06-tracking.md）
**這章回答什麼**：業務窗口和維護文件的人看這章，知道每條需求目前確認到哪、驗收到哪。
**從來源哪裡找**：不讀來源 Spec。資料全來自你已寫好的 `04-requirement-index.md`（每個需求鍵一列）和 `07-assumptions.md`（備註引用假設編號）。
**寫法**：
### 6.1 追蹤表
- 從 04 索引由上而下逐列產生，每個需求鍵一列，順序與 04 相同，「排除」的也要列。
- 表頭逐字照抄，不增減欄：

`| 需求鍵 | 摘要 | 確認狀態 | 確認人／日期 | 驗收結果 | 驗收日期 | 備註 |`

| 欄 | 初寫時怎麼填 |
|---|---|
| 需求鍵、摘要、確認狀態 | 照 04 索引抄，不改寫 |
| 確認人／日期 | `—`；之後填「代稱／日期」 |
| 驗收結果 | `—`；之後只填 `通過` 或 `未通過`，只由 9.2 的紀錄決定 |
| 驗收日期 | `—` |
| 備註 | 確認狀態 `待確認` → `見 A-###`（照索引的「相關假設」）；`排除` → 排除原因；其餘 `—` |

### 6.2 狀態值
確認狀態只有下列 5 個值：

| 值 | 意思 | 誰能設 | 怎麼設 |
|---|---|---|---|
| 待確認 | 內容還不能當定案：來源標為草稿、缺證據，或有開放的假設 | 你（初寫、7.1 發現缺口、8.2 重新確認）；人 | 在追蹤表改；同步 04 與該需求完整內容所在的檔 |
| 已確認 | 內容清楚，且沒有開放的假設影響它 | 你（初寫：來源標示已確認或沒有標示，且內容清楚）；業務窗口（人工確認） | 同上；人工確認要填確認人／日期 |
| 已交付 | 這條需求已做進成品 | 只有人 | 只改追蹤表 |
| 已驗收 | 業務人員實際操作後通過（9.2 有紀錄） | 只有人 | 只改追蹤表，並填驗收結果、驗收日期 |
| 排除 | 來源標為排除，或需求因 Spec 改版刪除 | 你（來源標排除；8.2 的刪除） | 同「待確認」；備註寫原因，保留該列 |

- 允許的轉移：待確認 → 已確認 → 已交付 → 已驗收；任一值 → 排除；已確認、已交付、已驗收 → 待確認（只因為重開假設或 8.2 重新確認）。其他轉移不要做。
- 你只能設 `待確認`、`已確認`、`排除`。看到 `已交付`、`已驗收` 不要改。
- 確認狀態改成 `待確認`、`已確認`、`排除` 時，追蹤表、04 索引、該需求完整內容所在檔三處同改。`已交付`、`已驗收` 只在追蹤表；04 與完整內容所在檔是 `已確認` 時，追蹤表可以是 `已確認`、`已交付`、`已驗收`。

**找不到或有問題時**：04 某列缺摘要或確認狀態 → 回去補 04，不在追蹤表自己補。追蹤表與 04 列數不同 → 以 04 為準重產。
**不要寫**：排程、負責人指派、預計完成日；不要加欄；不要改摘要文字。
**範例**：
```
| 需求鍵 | 摘要 | 確認狀態 | 確認人／日期 | 驗收結果 | 驗收日期 | 備註 |
|---|---|---|---|---|---|---|
| FLOW-001 | 申請人填借用單並送審 | 已確認 | — | — | — | — |
| RULE-003 | 借用期間最長 7 天，超過不能送審 | 待確認 | — | — | — | 見 A-002 |
```

## 第 7 章 缺口、矛盾與假設（輸出檔：07-assumptions.md）
**這章回答什麼**：業務窗口和 Spec 產製端看這章，知道來源哪裡不夠、你暫時怎麼處理、要問誰。
**從來源哪裡找**：寫第 3～9 章時隨時發現。另外找來源自帶的問題清單：標題或內文有「問題」「待確認」「未決」「Open」「TBD」「TODO」的段落或表格。
**寫法**：
### 7.1 什麼算缺口
對每個疑點依序問，第一個符合的就是它的類型：

| 順序 | 類型 | 判斷規則 | 例 |
|---|---|---|---|
| 1 | 矛盾 | 兩處（含同檔兩節）對同一件事的說法不能同時成立 | 一處寫借用期間最長 7 天，另一處寫 14 天 |
| 2 | 未完成 | 來源自己標示草稿、待補、待確認、TBD，或內容是佔位（「略」「同上」但上面沒有） | 規則表「逾期處理」格寫「待補」 |
| 3 | 看不懂 | 讀完仍無法用一句話講出「誰、在什麼條件下、得到什麼結果」，或用了來源沒定義的代碼或縮寫 | 「類型 B 走簡易流程」，沒說類型 B 是什麼 |
| 4 | 缺漏 | 來源提到一件事，但少了第 5 章標「必答」的欄位，或少了寫需求必要的一項（條件、結果、角色、代碼值、訊息） | 寫「逾期要通知」，沒寫通知誰 |

不算缺口：
- 兩處說法可以同時成立（一般規則加例外）→ 兩條都寫成需求。
- 來源明說「本期不做」「不適用」→ 寫成 SCOPE 排除。
- 只涉及系統設計的疑問（資料怎麼存、怎麼實作）→ 不登記。
- 第 5 章非必答欄填 `—`（來源沒提）→ 不登記。

每筆假設至少掛一個需求鍵。找不到現有需求可掛 → 在 5.8 末尾「其他」開一條 OTHER 需求，描述寫「〈缺什麼〉：來源未涵蓋」，確認狀態 `待確認`，再掛假設。

### 7.2 假設登記
發現就立刻追加一列，編號取下一個 `A-###`（A-001 起依序給號，不重用、不改號）。表頭逐字照抄：

`| 編號 | 類型 | 缺什麼 | 暫定做法 | 影響的需求鍵 | 該問誰 | 狀態 | 關閉依據 |`

| 欄 | 怎麼填 |
|---|---|
| 類型 | 7.1 的四個值之一 |
| 缺什麼 | 一句業務語言，句末加「（來源：`<檔名> §<節>`）」；矛盾的兩處都寫 |
| 暫定做法 | 見下表；選對業務最保守的 |
| 影響的需求鍵 | 所有受影響的鍵，用頓號分開，至少一個，且都在 04 索引裡；整類來源未涵蓋時寫 `整類：〈類別碼〉` |
| 該問誰 | 見下表，只填一個：`業務窗口` 或 `Spec 產製端` |
| 狀態 | 初寫一律 `開放` |
| 關閉依據 | 開放時 `—`；關閉時見 7.4 |

「最保守」＝錯了對業務傷害最小。暫定做法照下表寫，不要自己發明；不可寫「照一般做法」「依慣例」；不可比來源任何一處寫的更寬鬆。

**暫定做法表**（第 3、5、9 章各節提到的暫定做法都以本表為準）：

| 缺的是 | 暫定做法（照寫） |
|---|---|
| 誰可以做某動作、看某資料 | 不允許；待業務窗口確認 |
| 資料範圍（能看到哪些人的資料） | 本人 |
| 欄位是否必填 | 必填 |
| 預設值、自動帶入的來源 | 不自動帶值；由使用者填 |
| 某狀態轉移是否允許；來源沒寫到的轉移 | 不允許該轉移 |
| 規則的條件、門檻或邊界 | 採較嚴格的解讀（擋下的範圍較大），並寫明採哪一種 |
| 分不出阻擋或警告 | 阻擋 |
| 訊息原文 | 以條件文字作訊息，待業務窗口給原文 |
| 代碼值或選項 | 只接受來源已列出的值 |
| 代碼值的意思 | 照代碼值原文顯示，待確認意思 |
| 失敗或例外時的處理 | 流程停在原狀態，由人工確認 |
| 來源提到、但沒寫的例外路徑 | 不提供該路徑 |
| 兩處說法矛盾 | 採限制較多的一邊，並寫明是哪一邊 |
| 看不懂的自動處理或條件 | 不自動執行；由人工處理 |
| 來源只有圖、截圖或技術結構 | 照它寫出業務意思，待確認 |
| 整類需求來源沒提 | 視為無此類需求 |
| 本期範圍未明列 | 以來源描述到的功能為範圍，未描述的不做 |
| 來源標草稿、待確認的內容 | 照草稿內容寫，暫以草稿為準（不比來源寬鬆） |
| 來源有列的轉移，但觸發者或條件缺 | 暫不提供該轉移 |

該問誰：答案是業務要決定的事（規則、權限、選項、誰負責）→ `業務窗口`；答案是舊系統已經存在的事實（來源漏列、代碼的意思、矛盾哪邊正確）→ `Spec 產製端`。矛盾、看不懂預設 `Spec 產製端`；兩者難分 → `Spec 產製端`。

登記後，把 `A-###` 填進每個受影響需求的「相關假設」欄，並把它的確認狀態設為 `待確認`（6.2 同步規則）。

### 7.3 接來源的問題清單
- 來源有問題清單 → 每題一列，一題都不漏。表頭逐字照抄：

`| 來源問題 | 對應假設或答案位置 | 說明 |`

- 「來源問題」：`<檔名> §<節> 第 N 題` 加一句摘要。
- 「對應假設或答案位置」只有三種寫法：`A-###`；`來源已答：<檔名> §<節>`；`不適用：屬系統設計`。
- 判斷「來源已答」：來源另一處有明確結論句。只有「建議」「傾向」不算已答，要登記假設。
- 來源沒有問題清單 → 本節不放表，只寫一行：`來源無問題清單`。

### 7.4 怎麼關閉假設
只在兩種情況關閉，其他時候不要自己關：
- 業務窗口回覆（人給你回覆文字）。
- Spec 產製端補查後出新版（走第 8 章；新版有補才關）。

關閉步驟：
1. 7.2 該列：狀態改 `已關閉`；關閉依據寫「〈日期〉〈回覆人代稱〉：〈結論一句〉」，新版補查則寫「新版〈版本〉 `<檔名> §<節>`」。「暫定做法」保留不改。
2. 把結論改寫進每個受影響需求的描述；來源欄加註「；A-### 回覆」。需求鍵不變。
3. 受影響需求：它的相關假設全部 `已關閉` → 確認狀態改 `已確認`；仍有 `開放` 的 → 維持 `待確認`。追蹤表同步改確認狀態，並填確認人／日期、備註。
4. 7.3 對應列：保留 `A-###`，說明加「已關閉」。5.8 該類「還缺什麼」同步更新。
5. 回覆與來源 Spec 衝突 → 仍依回覆關閉，並在追蹤表備註寫「來源待更正」，請 Spec 產製端改版。

**找不到或有問題時**：缺的資訊要寫成需求才寫得下去，就先登記假設，需求描述只寫來源有的部分，其餘寫「來源未涵蓋」。
**不要寫**：系統設計問題；你自己拍板的結論；沒有需求可掛、與業務行為無關的好奇問題；開放假設的「關閉依據」。
**範例**：
```
| 編號 | 類型 | 缺什麼 | 暫定做法 | 影響的需求鍵 | 該問誰 | 狀態 | 關閉依據 |
|---|---|---|---|---|---|---|---|
| A-002 | 矛盾 | 借用期間上限，一處寫 7 天、一處寫 14 天（來源：03-rules.md §1 第 3 列；03-rules.md §4） | 採限制較多的一邊：最長 7 天 | RULE-003、ACC-009 | Spec 產製端 | 開放 | — |
| A-005 | 缺漏 | 核准後可否改借用期間（來源：05-flow.md §5 第 2 題） | 不允許該轉移 | STATE-006 | 業務窗口 | 已關閉 | 2026-11-12 業務窗口甲：核准後不可改 |

| 來源問題 | 對應假設或答案位置 | 說明 |
```

## 第 8 章 Spec 改版（輸出檔：08-spec-change.md）
**這章回答什麼**：來源 Spec 出新版時，業務需求文件怎麼跟著改，而且不弄亂已發布的編號。
**從來源哪裡找**：初寫時只需要來源版本標示（見 2.4）。改版時才比對新舊版 Spec。
**寫法**：
### 8.1 新舊版並存
初寫時照抄下列固定文字並填空，之後每次改版只更新「目前來源版本」。

**固定文字**：
> 目前來源版本：〈版本標示〉；取得日期：〈日期〉；位置：`<來源資料夾>`。
> 來源 Spec 出新版時，舊版留在原處，不刪、不改。新版放在另一個資料夾 `<來源資料夾>-〈新版本〉`。
> 業務需求文件只有一份，在 `<輸出資料夾>` 就地更新，不另存新資料夾。
> 每次改版在本檔「Spec 差異報告」追加一段，標明新舊版本與日期，不覆蓋舊段。

來源沒有版本標示 → 版本標示寫「來源未標示」，取得日期用你開始工作的日期。
### 8.2 差異處理
**固定文字**：
> 改版依下列順序處理：
> 1. 差異比對：逐檔比對新舊版（標題、表格列、代碼值、訊息文字），每個差異列成「Spec 差異報告」一列，類型只有新增、修改、刪除。
> 2. 需求鍵增刪改：新增 → 新需求鍵（該類別續號）；修改 → 改寫原需求的描述與來源，需求鍵不變；刪除 → 該列保留，確認狀態改「排除」，備註寫「Spec 〈版本〉已刪除」。
> 3. 影響評估：找出引用被改需求鍵的 FLOW，以及「來源需求鍵」含該鍵的 ACC，填入差異報告「影響的情境與驗收」。
> 4. 重新確認：受影響的需求（含其 ACC）確認狀態一律改回「待確認」；追蹤表的驗收結果與驗收日期改 `—`，備註寫「Spec 〈版本〉修改，需重新確認」。
> 5. 同步：更新 04 索引、追蹤表、07 假設（新版已補的依 7.4 關閉；新版新出現的缺口登記新 A-###）、9.1 的衍生情境，最後更新 8.1 的目前來源版本、2.4 與 README 文件資訊的「根據的來源 Spec 版本」。

Spec 差異報告表頭（逐字照抄）：

`| 項次 | 來源位置 | 類型 | 舊內容摘要 | 新內容摘要 | 影響的需求鍵 | 處理 | 影響的情境與驗收 |`

「處理」只有四個值：`新增需求`、`改寫需求`、`排除需求`、`無需求影響`。初寫時本檔差異報告只放表頭和一行 `（尚無改版）`。

### 8.3 需求鍵穩定性
**固定文字**：
> 需求鍵發布後不改、不重用。刪除的需求保留原列，確認狀態改「排除」並寫原因。假設編號 A-### 同樣不改、不重用。

**找不到或有問題時**：新舊版對不上（檔被拆併、章節改名）→ 以業務內容比對，不以檔名比對；仍無法判斷是不是同一件事 → 當作「刪除加新增」，並登記一筆類型「看不懂」的假設。
**不要寫**：新版的系統設計變動；沒有對到來源位置的差異；因為改版而重編舊需求鍵。
**範例**：
```
| 項次 | 來源位置 | 類型 | 舊內容摘要 | 新內容摘要 | 影響的需求鍵 | 處理 | 影響的情境與驗收 |
|---|---|---|---|---|---|---|---|
| 1 | 03-rules.md §1 第 3 列 | 修改 | 借用期間最長 7 天 | 最長 14 天 | RULE-003 | 改寫需求 | FLOW-001、ACC-009 |
| 2 | 04-states.md §2 | 刪除 | 「報廢」狀態 | （無） | STATE-007 | 排除需求 | ACC-014 |
```

## 第 9 章 業務驗收（輸出檔：09-acceptance.md）
**這章回答什麼**：業務人員看這章，知道要操作哪些情境、怎麼算通過、什麼時候算本期完成。
**從來源哪裡找**：先找來源有沒有驗收或測試情境：標題含「驗收」「測試」「情境」「Acceptance」「Test」，或內文有「假設／當／則」「Given／When／Then」的段落。再從你已寫好的 03、05 各檔取需求鍵。
**寫法**：
### 9.1 驗收情境
ACC 需求在這裡編號（`ACC-001` 起依序給號）並寫完整內容。表頭逐字照抄：

`| 需求鍵 | 情境 | 前置條件 | 操作步驟 | 預期結果 | 來源需求鍵 | 衍生 | 來源 | 確認狀態 | 相關假設 |`

寫法：
1. 來源有寫的情境先寫，照來源順序。內容照用，不增刪業務意思；衍生欄 `否`；來源欄寫位置；來源需求鍵填它驗證的需求鍵（多個用頓號）。來源缺前置條件或操作步驟 → 依它驗證的需求補寫，不算缺口、不登假設；只有缺預期結果才寫 `來源未涵蓋` 並登記假設。
2. 再依下表衍生，來源沒有才衍生：同一條路徑來源已有情境驗證，就不再衍生。衍生欄 `是`；來源欄寫「衍生（見來源需求鍵）」；來源需求鍵只填一個（UI 合併的情境例外：填該組全部欄位列，頓號分開）；情境欄開頭加【類型】。
3. 預期結果只寫業務上看得到的結果：畫面訊息、單據狀態、收到的通知、能或不能做某事。不寫系統內部行為。
4. 確認狀態：來源需求鍵全是 `已確認` → `已確認`；任一個是 `待確認` → `待確認`，相關假設照抄那些需求的假設，預期結果依暫定做法寫。

| 來源需求類別 | 每個要衍生的情境 |
|---|---|
| FLOW | 每條 FLOW 需求 1 個：正常路徑標【正常】、例外路徑標【例外】 |
| RULE | 每條【成立】1（條件成立時看得到的結果）；條件有數值、日期或次數門檻時再加【邊界】1（剛好等於門檻）；【不成立】不衍生（條件不成立就是正常路徑，已由 FLOW 驗證） |
| STATE | 「允許」的轉移：已出現在任一 FLOW 步驟（→ STATE-###）的不衍生，其餘各【允許】1；來源點名的「禁止」轉移各【禁止】1；「（其他未列出的轉移）」列與狀態表的列不衍生 |
| PERM | 不衍生【允許】（由 FLOW、STATE 的情境驗證）；同一對象有不可的角色時【拒絕】1（步驟寫用不可的角色操作）；資料範圍不是「全部」的列【拒絕】1（看不到範圍外的資料）；角色定義列不衍生 |
| UI | 每個畫面：必填欄為「必填」、且可改的欄位合併【未填】1（步驟列出這些欄位）；「〈條件〉時必填」「〈條件〉時可改」「〈條件〉時出現」依條件文字分組，條件相同的欄位合併，每組【條件】1（步驟分「條件成立」「條件不成立」兩段）；畫面列、動作列、唯讀欄不衍生 |
| EXT | 每條 EXT 需求【失敗】1：預期結果照「失敗時業務處理」；是 `來源未涵蓋` 就照暫定做法寫 |
| SCOPE、DATA、OTHER、ACC | 不衍生 |

需求本身沒寫結果，預期結果無從寫 → 寫「來源未涵蓋」，並掛該需求已有的假設，沒有就新登記。編號順序：來源有寫的在前，衍生的在後，依 FLOW、RULE、STATE、PERM、UI、EXT 排。

### 9.2 業務人員實際操作與驗收紀錄
- 由業務人員在成品上照 9.1 的步驟實際操作。你不填結果，初寫時本節只放表頭和一行 `（尚無紀錄）`。表頭逐字照抄：

`| 項次 | ACC 需求鍵 | 操作人（代稱） | 操作日期 | 實際結果 | 結果 | 差異說明 | 後續處理 |`

通過標準（三項都成立才填 `通過`）：
1. 操作人是業務人員，不是開發者，也不是你。
2. 照該 ACC 的前置條件與操作步驟做。
3. 實際結果在業務上看得到的部分，與預期結果逐句一致。

任一項不成立填 `未通過`，差異說明寫哪裡不同；「後續處理」只有三個值：`修正成品`（需求寫對、做錯）、`新增假設`（需求本身缺或錯，回 7.2 登記）、`無`。

一條需求的驗收結果：所有以它為來源需求鍵的 ACC 都有 `通過` 的最新紀錄 → `通過`，否則 `未通過`；沒有 ACC 的需求維持 `—`。結果由人更新到追蹤表。
